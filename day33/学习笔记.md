# Day33：RocketMQ

## 学习目标

理解 RocketMQ 的核心概念，与 RabbitMQ 对比，掌握 Topic、Producer、Consumer、Consumer Group、Offset、Retry、DLQ。

## 环境

- RocketMQ 5.3.0（Docker 容器 `day33-rocketmq`）
- NameServer: `127.0.0.1:9876`
- Broker: `127.0.0.1:10911`

## §1 核心概念

### 1.1 Topic

**Topic** 是消息的逻辑分类。Producer 发消息到 Topic，Consumer 订阅 Topic。

与 RabbitMQ 的 Exchange 不同，RocketMQ 的 Topic 本身不决定路由规则，而是直接作为消息存储单元。

### 1.2 Producer

**Producer** 发送消息到 Topic。支持同步发送、异步发送、单向发送。

```java
DefaultMQProducer producer = new DefaultMQProducer("producer-group");
producer.setNamesrvAddr("127.0.0.1:9876");
producer.start();
producer.send(new Message("topic", body.getBytes()));
```

### 1.3 Consumer

**Consumer** 从 Topic 拉取消息。RocketMQ 支持两种模式：

- **PushConsumer**：Broker 主动推消息（底层仍是拉取，封装成推）
- **PullConsumer**：应用主动拉取

### 1.4 Consumer Group

**Consumer Group** 是一组 Consumer 的集合。同一 Group 内的 Consumer 共同消费一个 Topic，实现负载均衡。

关键规则：
- 同一 Group 内，一条消息只被一个 Consumer 消费（集群模式）
- 不同 Group 之间，消息互相独立，各自消费

### 1.5 Offset

**Offset** 是消息在队列中的位置。Broker 为每个 Consumer Group 记录消费进度（Offset）。

- 消费成功后，Offset 前移
- 重启 Consumer 时，从上次 Offset 继续消费
- 可以手动重置 Offset 重新消费

### 1.6 Retry

**Retry** 是消费失败后的自动重试机制。

- 默认重试 16 次，间隔递增（10s, 30s, 1m, 2m...）
- 重试消息进入 `%RETRY%consumerGroup` 队列
- 重试次数耗尽后进入 DLQ

### 1.7 DLQ（死信队列）

**DLQ**（Dead Letter Queue）存储重试耗尽的消息。

- 队列名：`%DLQ%consumerGroup`
- 需要人工处理或特殊逻辑处理

## §2 与 RabbitMQ 对比

| 维度 | RabbitMQ | RocketMQ |
|------|----------|----------|
| 路由模型 | Exchange + Binding + Routing Key | Topic + Tag/SQL92 过滤 |
| 消费模式 | Push（推） | Push/Pull（封装成推） |
| 消息存储 | 队列（Queue） | 队列（Queue）+ 索引 |
| 顺序消息 | 单队列单消费者 | 队列内有序 |
| 延迟消息 | 插件支持 | 原生支持（18 个级别） |
| 事务消息 | 不支持 | 原生支持 |
| 吞吐量 | 万级 | 十万级 |
| 适用场景 | 企业级应用、复杂路由 | 电商、金融、大数据 |

## §5 常见问题

### 5.1 为什么 Consumer 收不到消息？

排查步骤：
1. Topic 是否创建？`sh mqadmin topicList -n localhost:9876`
2. Consumer Group 是否注册？`sh mqadmin consumerProgress -n localhost:9876 -g day33-task-consumer-group`
3. Broker 地址是否正确？`sh mqadmin clusterList -n localhost:9876`
4. 防火墙是否放行 9876/10911 端口？

### 5.2 消息重复消费

RocketMQ 保证**至少一次**投递，不保证**仅一次**。Consumer 需实现幂等性。

### 5.3 消息顺序

- 全局有序：单 Topic 单队列，性能差
- 分区有序：同一 Key 的消息进入同一队列，保证局部有序

## §6 学员作答与批语（2026-09-22）

### 问题 1：RocketMQ 的 Topic 与 RabbitMQ 的 Exchange 有什么区别？

**学员作答**：topic相比exchange只包含队列信息而不包含路由信息，只作为信息存放

**批语**：✅ 方向正确，但有一处需要精确：**Exchange 也不存消息**。RabbitMQ 里存消息的是 Queue，Exchange 只做路由转发（按 Binding + Routing Key 决定扔进哪些 Queue）。所以准确的对比是：

- RabbitMQ：**Exchange（纯路由）→ Queue（存储）**，两段式，路由逻辑在 Broker 侧
- RocketMQ：**Topic（逻辑分类）→ MessageQueue（存储）**，Topic 本身就是存储单元；路由/过滤弱化——Producer 直接选队列（可用 `MessageQueueSelector` 按 Key 指定），Consumer 侧用 Tag/SQL92 过滤

一句话：RabbitMQ 把「路由」做成了一等公民，RocketMQ 把路由砍到最薄换取高吞吐。

### 问题 2：Consumer Group 的作用是什么？同一 Group 和不同 Group 的行为差异？

**学员作答**：可以实现对消息的1对n处理，同一group内消息是作为1对1，但对于不同group则相当于1对多，支持来自不同group的单个消费者进行消费

**批语**：✅ 完全正确，这就是标准答案的骨架。补充两点工程细节：

1. 组内 1 对 1 是**默认的集群模式（CLUSTERING）**：同 Group 的多个 Consumer 瓜分队列，一条消息只被其中一个消费，实现负载均衡。RocketMQ 还支持**广播模式（BROADCASTING）**：同 Group 内每个 Consumer 都收到全量消息（如本地缓存刷新场景），用 `consumer.setMessageModel(MessageModel.BROADCASTING)` 切换。
2. 组间 1 对 n 的本质：每个 Group 有**自己独立的 Offset**，互不干扰——所以新加一个 Group 订阅同一 Topic，就能从头（或从最新）完整消费一遍，这就是「一条消息多个业务方各自消费」的实现原理。

### 问题 3：Offset 是什么？为什么重启 Consumer 后不会重复消费？

**学员作答**：消费者消费信息的进度，重启consumer则会从上次offset位置进行继续消费

**批语**：✅ 正确。深化三个点：

1. **粒度**：Offset 是按「Consumer Group × MessageQueue」二维记录的（Broker 端持久化在 `consumerOffset.json`），不是整个 Topic 一个进度。
2. **「不重复」有条件**：消费成功后 Offset 才会提交（Push 模式默认异步批量提交）。如果消费成功但 Offset 尚未提交时宕机，重启后会**重复消费一小段**——这就是 RocketMQ「至少一次投递」语义的来源，Consumer 必须做幂等。
3. **可重放**：运维可通过 `mqadmin resetOffsetByTime` 把 Offset 拨回历史时间点，实现消息重新消费——排障和补数据的利器。

## §7 总结

Day33 完成了 RocketMQ 基础概念的学习，通过 Docker 部署了 RocketMQ 5.3.0，并运行了 Producer/Consumer 演示。关键收获：

1. RocketMQ 的模型比 RabbitMQ 更简单：Topic 直接存储消息，无需 Exchange/Binding
2. Consumer Group 实现负载均衡和广播消费
3. Offset 机制保证消费进度可恢复
4. 与 RabbitMQ 相比，RocketMQ 更适合高吞吐、大数据场景
