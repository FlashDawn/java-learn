## 1. 概念

### 1.1 ACK

- **是什么：** Consumer 告诉 Broker「这条我处理完了，可以删」。
- **为什么需要：** Broker 发出去不等于处理完。只有收到 ACK，才把消息从队列里删掉。
- **怎么做：** 手动确认：`basicConsume(queue, false, ...)` 关掉自动确认，处理成功后 `channel.basicAck(tag, false)`。
- **代码：** `Day31App` 里 `channel.basicAck(tag, false)`
- **坑：** 自动确认（`autoAck=true`）在消息一送达就删。Worker 还没处理就崩了，消息已经没了。

### 1.2 NACK

- **是什么：** Consumer 告诉 Broker「这条我处理不了」。
- **为什么需要：** 失败不能假装成功。NACK 让 Broker 知道这条要重新安排。
- **怎么做：** `channel.basicNack(tag, false, requeue)`。`requeue=true` 回队列再试；`false` 丢弃或进死信。
- **代码：** `Day31App` 里两处 `basicNack`
- **坑：** 失败就 NACK requeue=true，但不限制次数。同一条消息永远失败，就在队列里无限循环，Worker 被它卡死。

### 1.3 Retry

- **是什么：** 失败后重新投递。本日用 NACK requeue=true 实现。
- **为什么需要：** 临时故障（网络抖一下、数据库连接池满）不该让整条消息报废。
- **怎么做：** 记录每条消息的尝试次数；第一次失败回队列，第二次成功就 ACK。
- **代码：** `attempts.merge(id, 1, Integer::sum)` + `basicNack(tag, false, true)`
- **坑：** 重试没有间隔。消息立刻回队列，立刻又被同一个 Worker 拿到，失败-重试-失败，把 CPU 打满。生产要加延迟（TTL + 延迟队列，或退避算法）。

### 1.4 Dead Letter Queue

- **是什么：** 收「处理不了」的消息的队列。本日 `day31.dlq`。
- **为什么需要：** 有些消息永远失败（数据本身有问题）。不能让它无限重试，也不能直接删掉，要留个案发现场。
- **怎么做：** 业务队列声明时带 `x-dead-letter-exchange` 和 `x-dead-letter-routing-key`。被 NACK 且 requeue=false 的消息会被 Broker 搬到 DLX，再进 DLQ。
- **代码：** `setup` 里的 `queueArgs`
- **坑：** 配了 DLX 却没人消费 DLQ。死信越堆越多，问题被藏起来。DLQ 要有告警或人工处理入口。

### 1.5 Prefetch

- **是什么：** Broker 一次最多给这个 Consumer 几条未确认消息。`basicQos(1)` = 一次一条。
- **为什么需要：** 不限制的话，Broker 会把队列里所有消息一次性推给一个 Worker。这个 Worker 崩了，所有消息都变成「已发未确认」，要重新投递。
- **怎么做：** `channel.basicQos(1)`。
- **代码：** `runWorker` 第一行
- **坑：** prefetch 设太大。一个 Worker 拿 1000 条，处理到第 3 条崩了，剩下 997 条全部要重投，其他 Worker 却在闲着。

| `setup` | 声明业务队列（带死信参数）、死信交换、死信队列 |

## 3. 与综合项目的关系

创建 Task 后投消息。Worker 消费时：
- 成功 → ACK，消息删；
- 临时失败 → NACK requeue，再试；
- 永远失败（比如任务数据不合法）→ NACK 进 DLQ，人工或定时任务处理。

Task 本身的状态不依赖消息是否被消费。消息只是「通知下游」，不是「事务的一部分」。

## 4. 自测

1. ACK 和 NACK 各在什么时候发？如果 Worker 处理到一半崩了，没来得及发任何确认，消息会怎样？
2. 为什么重试要限制次数？不限制会发生什么？
3. `basicQos(1)` 解决了什么问题？如果设成 100，一个 Worker 崩了会怎样？

### 学员作答与批语（2026-09-22）

**第 1 问**

> 学员：消费者处理完发 ACK，没法处理发 NACK；消息会被删除。

⚠️ **前半对，后半错。** 「处理完发 ACK、处理不了发 NACK」✅。但「Worker 崩了没发确认，消息会被删除」❌——**恰恰相反**：没收到 ACK，Broker 不删，消息标记为 Unacked 留在队列；等 Worker 连接断开，Broker 把这条消息**重新投递**给下一个 Worker。这正是手动 ACK 防丢的核心机制。

标准答案：

```text
Worker 处理到一半崩了（连接断开）：
  → Broker 没收到 ACK
  → 消息标记为 Unacked，不删
  → 连接断开后，Broker 把这条消息重新投递给下一个 Worker
  → 消息不丢，但可能被重复消费（Day32 的 at-least-once）
```

**第 2 问**

> 学员：重试没有间隔，不限制会反复投递，CPU 被占完。

✅ **通过。** 补：还会让这条坏消息永远挡在队列里，后面的消息排不上。

**第 3 问**

> 学员：解决了 Worker 遇到需要投递时，不用重新投递全部而是只投递上一个失败的消息。设成 100 则会因其中某一个失败而要发送全部消息。

⚠️ **方向反了。** Prefetch 不是「失败后只重投上一条」，而是**限制 Broker 一次推给 Worker 几条未确认消息**。`basicQos(1)` = 一次只给 1 条，Worker 崩了最多只有 1 条要重投；设成 100 = 一次推 100 条，Worker 崩了这 100 条全部要重投，而且其他空闲 Worker 拿不到活干。

标准答案：

```text
Prefetch 解决的是「Broker 一次推太多，Worker 崩了全部要重投」：
  basicQos(1)   → Broker 一次只给 1 条，Worker 崩了最多重投 1 条
  basicQos(100) → Broker 一次推 100 条，Worker 崩了 100 条全部重投
```

**闸门结论：第 2 问通过；第 1、3 问订正后通过。Day31 闭环。**
