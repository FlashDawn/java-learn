## 1. 概念

### 1.1 Provider 与 Consumer（服务提供方 / 消费方）

- **是什么**：一次 RPC 的两端。Provider 实现并暴露服务接口；Consumer 引用接口、像调本地方法一样发起远程调用。
- **为什么需要**：这就是「微服务之间怎么通话」的另一种答案。Day38 的答案是 HTTP + Feign；Dubbo 的答案是**私有 RPC 协议 + 接口代理**——调用双方共享一个 Java 接口（契约 jar），实现细节对 Consumer 完全透明。
- **怎么做**：
  - Provider：实现类加 `@DubboService`——做两件事：① 把本类发布为 RPC 服务（20880 端口监听）；② 向 Nacos 注册「接口全名 → 我的地址」；
  - Consumer：字段加 `@DubboReference`——注入的不是本地实现，而是 Dubbo 生成的 RPC 代理。
- **代码**：`day39-worker/.../WorkerServiceImpl.java`（`@DubboService`）、`day39-task/.../TaskController.java`（`@DubboReference`）
- **坑**：**`dubbo-spring-boot-starter` 不传递 `spring-boot-starter`**——worker 模块只引 dubbo starter 时编译直接报「程序包 org.springframework.boot 不存在」。Dubbo starter 假设你已有一个 Spring Boot 应用，只负责把 Dubbo 能力织进去；`@SpringBootApplication` 所必需的基础 starter 要自己显式引。

### 1.2 RPC（远程过程调用）

- **是什么**：`workerService.execute(job)` 这一行在 Consumer 进程执行，真正干活的代码在 Provider 进程——中间隔着网络。RPC 框架把「跨网络调一个方法」伪装成「本地方法调用」。
- **为什么需要**：与 HTTP 调用的本质区别不在「能不能调」，而在**协议效率与编程模型**：HTTP 是文本协议（JSON 序列化大、头部冗余、连接管理粗），Dubbo 协议是**TCP 长连接 + 二进制序列化**，单次调用开销小一个量级，适合服务间高频互调的内网场景。
- **怎么做**：一次调用的完整旅程（对照 `TaskController.dispatch` 里的那一行）：
  1. Consumer 调代理对象的 `execute(job)`；
  2. 代理把参数**序列化**成二进制（默认 Hessian2）；
  3. 向注册中心查「WorkerService 的 Provider 列表」（本地有缓存 + 订阅推送）；
  4. **负载均衡**挑一个 Provider；
  5. 走 **TCP 长连接**把请求发过去；
  6. Provider 反序列化 → 调真实实现 → 结果序列化回传；
  7. Consumer 反序列化，拿到返回值。
- **代码**：`day39-task/.../TaskController.java`（`dispatch` 方法——注释里写了这趟旅程）
- **实证（已通过）**：`GET 18110/tasks/dispatch?title=生成月度报表` 返回 `[task-service] 已派发，RPC 返回: worker 已完成任务 1: 生成月度报表`；同时 **worker 终端打印 `[Worker] RPC 收到任务: id=1, ...`、task 终端无此行**——证明执行真实地发生在另一个进程。worker 启动日志还可见注册 URL 实物：`dubbo://172.30.48.1:20880/com.example.day39.api.WorkerService?...&prefer.serialization=hessian2,fastjson2...`——接口全名、协议、序列化方式全在注册记录里。
- **坑**：RPC 的「像本地调用」是甜美的陷阱——**网络延迟、超时、失败都是本地调用没有的新问题**。把 RPC 当本地调用猛循环（for 循环里调 1000 次）是新手经典事故：本地调用是纳秒级，RPC 是毫秒级，差 6 个数量级。

### 1.3 Registry（注册中心）

- **是什么**：Provider 注册「接口名 → 地址」，Consumer 订阅「接口名 → Provider 列表」的中介。Dubbo 的注册中心**按接口维度**注册（不是按应用名），一个应用暴露 N 个接口就有 N 条注册记录。
- **为什么需要**：与 Day37 服务发现同一动机——消灭硬编码地址、支持弹性扩缩容。Dubbo 传统搭档是 ZooKeeper，3.x 时代 Nacos 已是一等公民，本日直接复用 day37-nacos。
- **怎么做**：`dubbo-registry-nacos` 依赖 + `dubbo.registry.address=nacos://127.0.0.1:8848`——Provider 与 Consumer 配同一行。
- **代码**：`day39-worker/src/main/resources/application.yml`、`day39-task/src/main/resources/application.yml`
- **坑**：Consumer 端 `dubbo.consumer.check=false` 的含义是「启动时不强制 Provider 在线」——默认 true 时，Consumer 启动发现 Provider 不在会直接启动失败；学习期关掉方便单独启停，生产按对依赖的强弱势决定。

### 1.4 契约 jar（api 模块）——Dubbo 的标志性工程结构

- **是什么**：`day39-api` 模块里只有两样东西：`WorkerService` 接口 + `TaskJob` 传输对象。Provider 依赖它来实现，Consumer 依赖它来调用——**双方共享的只有契约，没有实现**。
- **为什么需要**：这是 Dubbo 与 Feign 在工程结构上的分野。Feign 的接口写在 Consumer 侧（Consumer 单方面描述远程接口形状）；Dubbo 的接口是**独立发布的构件**，Provider 必须实现同一个接口——契约由「双方共同遵守」升级为「单一事实来源」，改接口 = 改契约 jar 版本，双方的编译器会逼着一起升级。
- **怎么做**：`day39-api` 打成普通 jar，worker 与 task 的 pom 各自依赖它。
- **代码**：`day39-api/.../WorkerService.java`、`TaskJob.java`；`day39/pom.xml`（modules 顺序：api 在最前）
- **坑**：契约 jar 里**只放接口和 DTO**——把实现类、工具类塞进去会导致「契约升级牵连面失控」，甚至把 Provider 的内部依赖漏给 Consumer。

### 1.5 Serialization（序列化）

- **是什么**：把 JVM 内存里的对象变成网络字节流（以及反向）的过程。Dubbo 默认用 **Hessian2**——二进制、紧凑、跨语言友好。
- **为什么需要**：对象不能上电线。序列化协议的选择直接决定 RPC 的开销：JSON 文本大约是同数据 Hessian2 二进制的 2~3 倍体积，且序列化/反序列化更耗 CPU。
- **怎么做**：跨网络传输的 DTO 三要素（本日用一次真实的失败换来的，见 §5 排障三）：
  1. `implements Serializable`——标识可序列化；
  2. **无参构造**——Hessian2 反序列化时先 new 一个空对象，再用反射逐字段注入；
  3. 字段有 getter/setter。

```java
public class TaskJob implements Serializable {
    private Long taskId;
    private String title;
    public TaskJob() { }           // Hessian2 反序列化必需的无参构造
    // ... 全参构造 + getter/setter
}
```

- **代码**：`day39-api/.../TaskJob.java`
- **坑（本日实测踩中）**：**不要用 `record` 当 RPC DTO**——record 没有无参构造、字段 final，Hessian2 在 Provider 侧解码时无法实例化，报 `Fail to decode request ... parameterTypes=null`，且 Dubbo 默认重试 2 次会把它放大成「Tried 3 times」。经典 JavaBean 才是 RPC 传输对象的安全形态。另两个生产坑：忘了 `implements Serializable` 的类编译期毫无异常、调用现场才炸；给 DTO **加字段是兼容的，改字段类型/删字段**会让新旧版本混跑时反序列化爆炸——契约演进只能加、不能改。

### 1.6 Load Balance（负载均衡）

- **是什么**：WorkerService 部署多个 Provider 实例时，Consumer 的代理按策略挑一个调用。Dubbo 默认 **random（按权重随机）**，另有 roundrobin、leastactive（最少活跃调用，最常用）、consistenthash（一致性哈希，用于有状态场景）。
- **为什么需要**：与 Day38 LB 同一动机。差别在位置：Spring Cloud 的 LB 是独立组件拦截 HTTP 请求；Dubbo 的 LB **长在 Consumer 代理内部**，是 RPC 旅程的第 4 步。
- **怎么做**：`@DubboReference(loadbalance = "leastactive")` 或在配置中心统一下发；本日单实例，未实操轮换。
- **代码**：机制内建于代理；策略名可通过注解/配置指定
- **坑**：leastactive 的「活跃数」统计的是** Consumer 侧自己发出的在途调用**——它看到的是局部视角，多 Consumer 场景下不与全局负载严格一致，通常够用，但别把它当成精确的全局调度。

## 3. 生产环境注意事项

1. **超时与重试必须成对思考**：Dubbo 默认重试 2 次（共 3 次调用）——对**幂等读**很友好，对**写操作**是灾难（一次超时可能实际写成功了，重试造成重复写）。写接口显式 `retries=0`，幂等靠业务关口（对照 Day35 的 DONE 状态关口）。
2. **契约 jar 的版本纪律**：接口变更只能加方法/加字段，不能改签名/改类型/删字段；升级时先升 Provider（兼容旧 Consumer），再滚动升 Consumer。
3. **注册中心挂了不影响存量调用**：Consumer 本地缓存了 Provider 列表，Nacos 短暂宕机时存量调用照常，只是新实例上不了线——但重启中的 Consumer 拿不到列表会启动失败，所以注册中心本身要集群（同 Day37 §3）。
4. **Dubbo Admin 值得部署**：官方治理控制台，可看注册关系、调权重、做 MOCK/降级开关；学习期跳过，生产必备。
5. **集群容错策略按接口选**：默认 Failover（失败换实例重试）；Failfast（快速失败，写操作用）；Failsafe（失败吞掉记日志，审计类用）；Broadcast（广播所有 Provider，本地缓存刷新类用）。

### 参考答案与批语（2026-10-16 学员作答）

**1. 为什么把 `WorkerService` 接口单独放进 `day39-api` 模块？Consumer 自己写一份同名同包的接口行不行，代价是什么？**

学员作答：因为 dubbo 协议缘故，单次调用开销小。

批语：⚠️ **偏题**——「单次调用开销小」本身没错（那是 §1.2 RPC vs HTTP 的结论），但它回答的是「为什么用 Dubbo」，不是「为什么要契约 jar」。标准答案分两层：

- **为什么独立成 jar**：Dubbo 的契约锚点是**接口全限定名**——Provider 必须 `implements` 同一个接口（JVM 类型系统的同一性），注册中心的注册键、代理的生成、序列化的类型元数据全部围绕它。接口独立发布 = **单一事实来源**：改接口就是改 jar 版本，**双方编译器会逼着一起升级**——Provider 改了方法签名，Consumer 一编译立刻报错，错误暴露在最早的时刻。
- **Consumer 自己抄一份行不行**：**技术上能跑**（Dubbo 运行期只认接口全限定名字符串，不校验字节码一致），但代价是放弃了契约 jar 的全部意义：① 编译期失去约束——Provider 改签名，Consumer 的副本浑然不觉，错误推迟到运行期才炸（对照 §5 排障二，NoSuchMethodError 这类运行期错误的排查成本远高于编译错误）；② 双份契约必然漂移——没有单一事实来源，两个副本随时间分叉；③ DTO（TaskJob）也得复制双份维护。Feign 能容忍 Consumer 单方面描述接口，是因为 HTTP 契约本来就是「URL + JSON 文本」，双方靠文档和纪律对齐；Dubbo 是二进制协议 + Java 类型系统，**契约 jar 就是类型安全的载体**。

**2. 从 `workerService.execute(job)` 到 Worker 真正执行经过哪几步？哪几步用到注册中心？**

学员作答：7 步，其中查 WorkerService 的 Provider 列表时用到了注册中心。

批语：✅ 正确（7 步旅程见 §1.2，注册中心用在第 3 步「查 Provider 列表」）。补一个精度修正：说「用到注册中心」更准确的说法是——**只有首次调用和列表变更时才真正访问注册中心**。稳态运行中，第 3 步查的是 Consumer **本地缓存的列表**（启动时拉取 + Nacos 主动推送变更）。这就是 §3 注意事项 3 的推论：**注册中心短暂宕机不影响存量调用**——已建立的 TCP 长连接和缓存列表照常工作，只是新实例上不了线、重启中的 Consumer 拿不到列表。把「注册中心」理解成「启动时的引路人 + 变更时的通知员」，而不是「每次调用的中转站」——调用流量根本不经过它，这也是 Dubbo 注册中心不承担流量压力、可以轻装部署的原因。

**3. 默认重试 2 次对「创建订单」写接口可能惹什么祸？怎么防？**

学员作答：默认重试 2 次会把失败放大成「Tried 3 times」，其余请补充。

批语：⚠️ 「放大成 3 次」说对了现象，但**没点破那个「祸」字**。核心一句话：**超时 ≠ 失败**。第一次调用很可能在 Provider 侧已经执行成功（订单已创建），只是响应慢/丢包，Consumer 判定超时后重试——于是**同一笔订单被创建 2~3 次**：重复扣款、重复发货。这就是本日排障三里你亲眼看到的「Tried 3 times」——对 record 那种必败的解码错误，重试只是放大报错；对写操作，重试放大的是**真实的数据事故**。防住要两层配合：

- **配置层**：写接口显式关掉重试——`@DubboReference(retries = 0)`（或全局 `dubbo.consumer.retries=0`）；按读写分治：幂等的查询接口保留默认重试（超时换台实例再试很划算），写接口零重试。
- **业务层（真正兜底）**：**幂等设计**——因为就算 Dubbo 不重试，网关重试、用户狂点按钮、上游重发都可能造成重复请求。手法对照 Day35 已学的族谱：① 请求方生成**唯一业务单号**传入，Provider 以它为去重键（唯一索引/去重表）；② **状态机关口**（已 DONE 的订单拒绝重复推进）。记住这个分工：**重试配置是「少惹祸」，业务幂等是「不怕祸」**——生产上写接口的幂等不是可选项。

## 5. 故障清单

1. **worker 编译失败：`程序包 org.springframework.boot 不存在`**（已修复）：`dubbo-spring-boot-starter` 不传递 `spring-boot-starter`——Dubbo starter 只织入 Dubbo 能力，假设宿主已是 Spring Boot 应用。修复：worker/task 模块显式引 `spring-boot-starter`（task 另需 `spring-boot-starter-web`）。
2. **task 启动报 `NoSuchMethodError: SpringFactoriesLoader.forDefaultResourceLocation(ClassLoader)`**（已修复）：父 pom 的 `dependencyManagement` 里 `dubbo-bom` 覆盖了 `spring-boot-starter-parent` 管理的 Spring 版本，把 spring-core/web/webmvc 全压到 **5.3.39**——Boot 3.3.5 的自动装配调用了 Spring 6.1 才有的方法，运行时炸出 NoSuchMethodError。修复：在父 pom 显式 import `spring-framework-bom:6.1.14` 且**放在 dubbo-bom 之前**（Maven 版本管理先声明先赢），`mvn dependency:tree` 复验 spring-core 回到 6.1.14。教训：**凡 BOM 混装，先跑 `dependency:tree` 看真实生效版本**；NoSuchMethodError/NoClassDefFoundError 十有八九是 classpath 版本打架。
3. **RPC 调用 500：`Fail to decode request ... parameterTypes=null`**（已修复）：`TaskJob` 最初写成 `record`——Hessian2 反序列化需要先 new 空对象再反射注入字段，record 没有无参构造且字段 final，Provider 侧解码直接失败；Dubbo 默认重试 2 次，错误被放大成「Tried 3 times of the providers」。修复：record 改经典 JavaBean（无参构造 + getter/setter + `implements Serializable`），重建后 RPC 一次通过。教训：**RPC DTO 用经典 JavaBean，别用 record**——除非确认序列化协议明确支持（fastjson2 支持，hessian2 不行）。
4. **Docker Desktop 卡死、Nacos 失联**（已解决）：C 盘剩余空间归零（WSL 虚拟磁盘在 C 盘），Docker 引擎停摆。修复：手动清理 C 盘（0.03GB → 8.15GB）+ 重启 Docker Desktop + `docker start day37-nacos`，全链路恢复。教训：Windows 上 Docker 的命根子在 C 盘，磁盘告警要当成一级事故；长期方案是把 Docker 的 WSL 数据（`wsl --export/--import`）与 Maven 本地仓库迁出 C 盘。
