## 1. 概念

### 1.1 REST API（User / Task）

- **是什么：** 用 HTTP 动词 + 资源路径表达对 User/Task 的操作。
- **为什么需要：** 前后端分离与服务间调用的统一契约。
- **怎么做：** `@RestController` + `@GetMapping`/`Post`/`Put`/`Delete`；路径变量与 JSON 体。
- **代码：**
  - `POST/GET/PUT/DELETE /users`、`GET /users` → `UserController`
  - `POST/GET /tasks`、`GET /tasks`、`PUT /tasks/{id}/status` → `TaskController`
- **坑：** 成功/失败 HTTP 状态要稳定；删除用 204 无 body 时客户端勿强解 JSON。

### 1.2 参数校验

- **是什么：** Bean Validation（`@NotBlank`、`@Email`、`@NotNull`…）+ 方法参数 `@Valid`。
- **为什么需要：** 把脏数据挡在 Controller 边缘，Service 少写 if。
- **怎么做：** `spring-boot-starter-validation`；DTO 注解；`@Valid @RequestBody`。
- **代码：** `UserRequest`、`TaskCreateRequest`、`TaskStatusRequest`
- **坑：** 忘了 `@Valid` 则注解不触发；嵌套对象还要 `@Valid` 级联。

### 1.3 全局异常

- **是什么：** `@RestControllerAdvice` 集中把异常变成统一 JSON。
- **为什么需要：** 避免每个 Controller try/catch；错误格式一致便于前端。
- **怎么做：** 分类型 `@ExceptionHandler`；计划格式 `{code,message,data}`。
- **代码：** `GlobalExceptionHandler` + `ApiResponse`
- **坑：** 最后兜底 `Exception` 别泄露堆栈给公网；本 Demo 带 message 仅供学习。

### 1.4 日志切面

- **是什么：** AOP 环绕 Controller，记方法、参数、耗时、异常（Day9 能力验收）。
- **为什么需要：** 排障要「谁调了什么、花了多久」；比每方法手写 log 干净。
- **怎么做：** `@Aspect` + `@Around` 切 `*Controller.*`。
- **代码：** `common/ApiLogAspect.java`
- **坑：** 参数可能含密码/token，生产必须脱敏；切面异常要决定是否吞掉（此处上抛）。

### 1.5 事务（Service）

- **是什么：** 写操作方法加 `@Transactional`；读可用 `readOnly=true`。
- **为什么需要：** 验收「会用事务边界」；日后换 JPA 时同一注解继续保护多表写。
- **怎么做：** Service 层标注；H2 提供 `PlatformTransactionManager`；业务仍内存仓库。
- **代码：** `UserService` / `TaskService`
- **坑：** 内存 Map 不会因回滚自动撤销（Day13 已讲）；此处重点是**边界放对层**。创建 Task 前校验 User 存在，避免孤儿任务。

### 1.6 重学深挖：一次请求的完整链路（2026-09-18）

**成功路径**（以 `POST /tasks` 为例）：

```text
Client → ServletContainer(Tomcat) → FilterChain → DispatcherServlet
  → HandlerMapping 找到处理器（注意：找到的是代理后的 Bean）
  → HandlerAdapter 调用：
      ① 参数解析 + @Valid 校验
         ← 失败：MethodArgumentNotValidException → @RestControllerAdvice → 400
         ⚠️ 此时方法体还没被调用，ApiLogAspect 根本没触发！
      ② 调用代理 → ApiLogAspect @Around 前置（记方法名、参数）
      ③ Controller 方法体 → Service 事务代理（开启事务）→ Repository
      ④ 事务提交 → 切面后置记耗时 → Jackson 序列化 → 200 + ApiResponse
```

**业务异常路径**（如创建 Task 时 User 不存在）：

```text
TaskService 抛 BusinessException
  → 事务代理捕获并回滚（内存 Map 无真实回滚，教学演示边界）
  → 切面 catch 记 warn → 必须 rethrow（Day9 的坑）
  → GlobalExceptionHandler → 统一 JSON {code, message, data}
```

**钉死的时序点**：`@Valid` 校验在 HandlerAdapter **参数解析阶段**，早于代理调用。所以：
- 校验失败路径：**切面不参与**，异常直接进 Advice；
- 业务异常路径：切面先（记 warn），Advice 后（转 JSON）。

这正是 §4 自测第 3 问更精确的答案。

### 1.7 重学深挖：三个设计决策（2026-09-18）

**① 为什么用 DTO（`UserRequest`）而不是直接收 `User` 领域对象？**
- 安全：直接绑定领域对象会遭 mass assignment（客户端多传 `role=admin` 就被赋值）；
- 校验注解不污染领域：`@NotBlank` 是入参约束，不是领域规则；
- 契约稳定：领域模型改字段不影响 API 契约。

**② 为什么 `@Transactional` 加在 Service 而不是 Controller？**
- 一个 Service 方法 = 一个业务用例 = 一个事务边界；Controller 只做 HTTP 编排；
- Controller 层事务会把事务范围扩大到序列化/视图渲染，连接占用变长；
- 失效写法：**自调用**（`this.method()` 不走代理）、**private 方法**（代理拦不到）。

**③ `PUT /tasks/{id}/status` 为什么单独成动作？**
- 状态变更是明确领域动作（可带状态机校验：done 不能回退）；
- 请求体只需 `{status}`，避免误改其他字段；
- 便于单独鉴权与审计。
