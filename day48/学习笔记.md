## 1. 概念

### 1.1 Compose 解决什么问题

Day46/47 的手工痛点：每起一个服务就要记一串 `docker run` 参数（网络、卷、端口、环境变量、启动顺序）。三个服务 = 三条命令 + 人工排序 + 人工记参数。

**Compose = 把「多容器应用」的拓扑声明在一个 YAML 里，一条命令整体起停。**

类比：单个容器是进程，Compose 文件是「进程组编排脚本」——而且是声明式的。

### 1.2 核心结构（当日文件骨架）

```yaml
name: day48            # 项目名 → 所有资源的前缀（day48-app、day48_backend、day48_pgdata）
services:              # 每个 service ≈ 一条 docker run 的参数集合
  app / postgres / redis
volumes:               # 命名卷，生命周期独立于 up/down
networks:              # 自建桥接网络，内部按服务名 DNS 解析
```

### 1.3 当日四个关键决策

**① `depends_on` + `condition: service_healthy`**
普通 `depends_on` 只保证「先启动」，不保证「已就绪」——应用比 DB 先监听端口就会连接失败。健康检查（postgres 用 `pg_isready`、redis 用 `PING`）+ `service_healthy` 条件才是正确姿势。当日日志实证：

```text
day48-postgres Healthy → day48-redis Healthy → day48-app Starting
```

**② 配置外置（镜像不变的秘诀）**

```yaml
environment:
  SPRING_APPLICATION_NAME: day14-api-compose
```

Spring Boot 宽松绑定：环境变量 `SPRING_APPLICATION_NAME` 覆盖 `application.yml` 的 `spring.application.name`。当日实证：日志应用名从 `day14-api` 变为 `[day14-api-compose]`，**镜像是同一个**。这就是 Day47 生产注意第 5 条的落地。

**③ 不对外发布内部端口**
`postgres`/`redis` 只出现在内部网络 `backend`，没有 `ports:` 映射——`docker compose ps` 里它们显示 `5432/tcp`（仅内部）。只有 `app` 发布 `18080:8080`。暴露面最小化；同时不与散养容器 `redis22`（宿主机 6379）冲突。

**④ 数据卷独立生命周期**
`docker compose down` 删容器、删网络，**但默认保留卷**；当日实证：down→up 后 `SELECT * FROM demo_note` 仍返回 `compose 持久化验证`。要连卷一起删需显式 `down -v`。

## 2. 原理：Compose 在背后做了什么

`docker compose up -d` 实际等价于：

```powershell
docker network create day48_backend
docker volume create day48_pgdata / day48_redisdata
docker run -d --name day48-postgres --network day48_backend ... postgres:16-alpine
docker run -d --name day48-redis    --network day48_backend ... redis:7-alpine
# 等两个健康检查通过 …
docker run -d --name day48-app --network day48_backend -p 18080:8080 -e ... day14-api:1.0
```

-  Compose 只是「读懂 YAML → 翻译成一串 Docker API 调用」的客户端工具，没有额外守护进程；
-  资源标签（`com.docker.compose.project=day48`）让它能找回并管理这组资源 → 才有 `down/ps/logs` 的整体操作；
-  `up` 是幂等的：配置没变则容器原样保留，变了只重建变化的 service。

## 3. 常见错误与排查

| 现象 | 根因 | 处理 |
|---|---|---|
| 应用启动报 DB 连接失败 | `depends_on` 没配健康条件，DB 还没就绪 | `condition: service_healthy` + 服务端 healthcheck |
| `docker compose` 命令不存在 | 旧版是 `docker-compose`（独立二进制） | Docker Desktop 自带 v2 插件，用空格写法 |
| 端口冲突 | compose 里发布的宿主机端口被占/保留 | 只改 YAML 里 `ports` 左侧 |
| down 后数据没了 | 用了 `down -v` 或数据没挂卷 | 数据目录必须挂命名卷；慎用 `-v` |
| 改了 YAML 不生效 | `up` 幂等，未触发重建 | `docker compose up -d --force-recreate` |
| 服务名 ping 不通 | 不在同一自建网络 | 检查 `networks:` 归属 |

## 4. 生产环境注意事项

1. **Compose 定位是「单机编排」**：多机集群上 K8s（Day51+）；生产常见用法是每机一份 compose；
2. **密码别进 YAML**：生产用 `.env` 文件（compose 自动读取）或 Docker secrets；学习日明文可接受；
3. **固定镜像版本**：别用 `latest`（呼应 Day46 生产注意）；
4. **资源限额**：生产加 `deploy.resources.limits`（compose v2 非 swarm 模式下用 `mem_limit`/`cpus`）；
5. **restart 策略**：`restart: unless-stopped` 应对进程崩溃与宿主机重启。

## 5. 预留：RabbitMQ / Nacos 怎么加

计划原文的五个服务，本日先落三个。日后学完 MQ/微服务，加服务只是往 `services:` 追加（以 RabbitMQ 为例）：

```yaml
  rabbitmq:
    image: rabbitmq:3.13-management-alpine
    volumes: [ "mqdata:/var/lib/rabbitmq" ]
    healthcheck: { test: ["CMD", "rabbitmq-diagnostics", "-q", "ping"], interval: 5s, retries: 10 }
    networks: [ backend ]
```

结构不变——这正是声明式编排的扩展性。

## 6. 闸门三问

1. `depends_on` 不加 `condition: service_healthy` 会有什么事故？健康检查在其中扮演什么角色？
2. 为什么 `postgres`/`redis` 不配 `ports:` 也能被 `app` 访问？这样做还顺带解决了什么冲突？
3. `docker compose down` 之后为什么数据还在？什么命令会把数据也删掉？

### 学员作答与批语（2026-09-18）

**第 1 问**

> 学员：会产生应用启动报 DB 连接失败。

✅ **通过。** 补全健康检查的角色：它是 **readiness 探针**——容器进程起来 ≠ 服务就绪（PostgreSQL 初始化数据目录要几秒）；`pg_isready`/`PING` 把「就绪」翻译成可轮询信号，`service_healthy` 才有依据可等。

**第 2 问**

> 学员：不对外发布内部端口，postgres/redis 只出现在内部网络 backend，没有 ports 映射。

✅ **通过。** 补两个关键词：自建 bridge 网络自带**按服务名 DNS 解析**（`postgres` → 容器 IP）；顺带解决的冲突是**宿主机 6379 已被散养容器 `redis22` 占用**。

**第 3 问**

> 学员：该命令不加可选项仅停止并删除容器+网络，保留卷；要删除得用 `docker compose down -v`。

✅ **通过。** 补一句边界：数据还在的前提是**数据写在挂载的命名卷里**；没挂卷的数据随可写层一起消失（Day46 分层原理）。

**闸门结论：三问全部通过，Day48 闭环。**
