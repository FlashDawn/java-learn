## 1. 概念

### 1.1 Exchange

- **是什么：** 收消息的入口。Producer 不把消息直接塞进某个队列，而是发给 Exchange。
- **为什么需要：** 一条「任务已创建」可能要同时通知邮件和审计。由 Exchange 决定抄送给谁，Producer 不用知道有哪些队列。
- **怎么做：** `channel.exchangeDeclare(名字, 类型)`。类型就是 direct / fanout / topic。
- **代码：** `Day30App` 里三次 `exchangeDeclare`
- **坑：** 发到一个没人绑定的 Exchange，消息被丢掉，Producer 默认还以为成功了。

### 1.2 Queue

- **是什么：** 真正存消息、等 Consumer 来取的地方。和 Day29 的队列是同一个角色。
- **为什么需要：** Exchange 只负责转发，不负责暂存。Consumer 慢的时候，消息停在 Queue 里。
- **怎么做：** `queueDeclare`。本日演示用非持久队列；进程或 Broker 重启会丢，持久化留到可靠性那天。
- **代码：** `bind` 方法里的 `queueDeclare`
- **坑：** 队列名是 Consumer 的地址。Producer 不应该把队列名写死，否则每加一个下游就要改生产者。

### 1.3 Binding

- **是什么：** 一条规则，把某个 Queue 挂到某个 Exchange 上，并带上 Binding Key。
- **为什么需要：** 没有 Binding，Exchange 不知道该把消息交给谁。
- **怎么做：** `channel.queueBind(queue, exchange, bindingKey)`。
- **代码：** `Day30App#bind`
- **坑：** 声明了 Exchange 和 Queue 却忘了 bind。发布成功，队列永远是空的。

### 1.4 Routing Key

- **是什么：** 这条消息自己带的标签，由 Producer 在发布时指定。它不是 Binding Key：Binding Key 贴在队列上，Routing Key 贴在消息上。
- **为什么需要：** 同一种 Exchange 才能按消息内容分流。`task.created` 和 `task.done` 走不同队列，靠的就是这个标签。
- **怎么做：** `basicPublish(exchange, routingKey, props, body)`。
- **代码：** `Day30App#publish`
- **坑：** 把 Routing Key 当成队列名。Direct 下两者经常碰巧写成同一个字符串，于是误以为「我是在指定队列」。

### 1.5 Direct

- **是什么：** Routing Key 与 Binding Key 完全相等才投递。
- **为什么需要：** 事件种类不多、要精确分流时用。创建走邮件，完成走短信。
- **怎么做：** `day30.email` 绑定 `task.created`，`day30.sms` 绑定 `task.done`。
- **代码：** `Day30App#direct`
- **坑：** 多绑一个相同的 key，那条消息会被复制到每个匹配队列。相等匹配不是「只给一个队列」。

实测：`task.created` 只进 email；`task.done` 只进 sms；email 再取一次是 `(empty)`。

### 1.6 Fanout

- **是什么：** 忽略 Routing Key。所有绑定到这个 Exchange 的队列都收到一份。
- **为什么需要：** 广播。任务创建后，邮件和审计都要知道，而且不打算按类型过滤。
- **怎么做：** 两个队列都 `queueBind(..., "")`，发布时 routing key 写成 `this-key-is-ignored`。
- **代码：** `Day30App#fanout`
- **坑：** 用 Fanout 做分流。它不会看 key，短信队列也会收到「已创建」。

实测：email 和 audit 都打印 `task 2 created`。

### 1.7 Topic

- **是什么：** Routing Key 按点分词。Binding Key 里 `*` 匹配一个词，`#` 匹配零个或多个词。
- **为什么需要：** 事件名会变长，例如 `task.created.email`。不想为每个精确字符串写一条 Direct 绑定。
- **怎么做：** `day30.created` 绑定精确的 `task.created`；`day30.all` 绑定 `task.#`。
- **代码：** `Day30App#topic`
- **坑：** `*` 和 `#` 搞反。`task.*` 匹配 `task.created`，不匹配 `task.created.email`。`task.#` 两个都匹配。

实测：`task.created` 进 created 和 all；`task.created.email` 只进 all，所以 created 的第二次拉取是 `(empty)`。

## 2. 代码导读

| 符号 | 职责 |
|---|---|
| `exchangeDeclare` | 声明入口和类型 |
| `queueDeclare` / `queuePurge` | 声明队列，并清掉上次运行留下的消息 |
| `queueBind` | 建立 Binding |
| `basicPublish` | Producer 发到 Exchange，并带上 Routing Key |
| `basicGet` | 演示用的拉取。真正的消费者是 Broker 推送，ACK 在 Day31 |

Spring 里以后对应：`RabbitTemplate.convertAndSend(exchange, routingKey, body)` 是发布；`Queue`、`Exchange`、`Binding` 三个 Bean 是声明；`@RabbitListener` 是 Consumer。今天不接 Spring，避免把路由规则藏进自动配置。

## 4. 自测

1. Exchange、Queue、Binding、Routing Key 各管什么？Producer 发布时指定的是哪一个？
2. 「任务已创建要同时给邮件和审计」用 Fanout 还是 Direct？如果还要单独接收 `task.created.email` 这种更长的名字，为什么改 Topic？
3. `direct` 方法里 email 第二次拉取为什么是 `(empty)`？消息去哪了？

### 学员作答与批语（2026-09-22）

**第 1 问**

> 学员：Exchange 接收并管转发方向；Queue 寄存等消费者拿；Binding 把 Queue 绑到 Exchange；Routing Key 是消息标签，由生产者制定。发布时指定 Routing Key。

✅ **大体通过。** 补半句：`basicPublish(exchange, routingKey, ...)` 指定的是 **Exchange + Routing Key**，不是队列名。Binding Key 贴在绑定上，和 Routing Key 是两样东西；Direct 下两者常写成同一个字符串，容易误以为「我在指定队列」。

**第 2 问**

> 学员：用 Fanout 让邮件和审计都知道；改 Topic 是为了像 IP 掩码一样，控制精确查找和广播。

✅ **通过。** Fanout 选对。隐喻微调：`*` / `#` 更像**通配符**（一个词 / 零到多个词），不是 CIDR 掩码的「前缀长度」。精确一条用 Direct 或精确 Binding；要 `task.created` 和 `task.created.email` 都能被同一条规则接住，才上 `task.#`。

**第 3 问**

> 学员：`task.created.email` 只进 all。更详细的请导师补充。

⚠️ **答偏了。** 题目问的是 **`direct` 方法**里 email 的第二次拉取，不是 Topic。标准答案：

```text
direct 段：
  publish task.created → 只进 day30.email
  publish task.done    → 只进 day30.sms
  第一次 pull email → 取出「task 2 created」（basicGet 自动确认，消息离开队列）
  第一次 pull sms   → 取出「task 2 done」
  第二次 pull email → (empty)：不是路由错了，是第一条已经被消费掉了
```

消息去哪了？进了演示代码的 `pull` 返回值（控制台那一行），不在别的队列里，也不在 Exchange 里。Exchange 不存消息。

#### Topic 补充（你提到的那条，一并钉死）

当日 Topic 绑定：

| 队列 | Binding Key | 含义 |
|---|---|---|
| `day30.created` | `task.created` | 精确相等 |
| `day30.all` | `task.#` | `task` 后面零个或多个词 |

两条发布：

| Routing Key | `day30.created` | `day30.all` |
|---|---|---|
| `task.created` | ✅ 进 | ✅ 进（`#` 可匹配零个词） |
| `task.created.email` | ❌ 不进（精确绑定不相等） | ✅ 进 |

所以：

- `topic created` 第一次有内容，第二次 `(empty)`：只有一条进了精确队列，已被第一次 pull 拿走；
- `topic all` 两次都有：两条消息都匹配了 `task.#`。

你说的「`task.created.email` 只进 all」对 Topic 成立；它解释不了 Direct 第二次为空。

**闸门结论：第 1、2 问通过；第 3 问纠正为 Direct「已被消费」后通过。Day30 闭环。**
