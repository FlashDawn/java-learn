## 1. 概念

### 1.1 Producer

- **是什么：** 生产消息的一方。本日是「任务创建成功后，发出一条 CREATED 事件」的代码。
- **为什么需要：** 把「任务已创建」和「发通知、记审计、刷新统计」拆开。Producer 不该认识这些下游。
- **怎么做：** 组一条 `Message`，交给 Broker，不直接调用通知逻辑。
- **代码：** `TaskEventProducer#publishTaskCreated`
- **坑：** 投递失败还当成功。`publish` 返回 false 时消息根本没进队列。

### 1.2 Consumer

- **是什么：** 消费消息的一方。只处理已经到达的 `Message`。
- **为什么需要：** 慢操作（发邮件、写审计）放在这里，就不挡创建任务的请求线程。
- **怎么做：** 从 Broker 取出消息，再执行业务。本日用 `handle` 里 `sleep 400ms` 模拟慢通知。
- **代码：** `TaskEventConsumer#handle`
- **坑：** 消费失败如果直接丢掉，这条任务事件就再也不会被处理。重试和死信是后面可靠性的内容，今天先记住「不能默默吞掉」。

### 1.3 Queue

- **是什么：** Broker 里暂存 Message 的队列。Producer 往里放，Consumer 从里取。
- **为什么需要：** 两边速度不一样。创建任务是毫秒级，发通知是几百毫秒。没有队列，快的一方只能干等慢的一方。
- **怎么做：** `LinkedBlockingQueue`，容量 8。`offer` 放不进去就返回 false，不无限堆积。
- **代码：** `Broker` 的 `queue` 字段
- **坑：** 无界队列会把消息堆在内存里直到 OOM。这和 Day7 的无界线程池队列是同一类问题。

### 1.4 Message

- **是什么：** 队列里的一条数据。本日包含消息 id、任务 id、事件名。
- **为什么需要：** 传的是「发生了什么」，不是把整个 `Task` 对象塞过去。下游只拿任务 id 再查，避免消息里的旧字段和数据库打架。
- **怎么做：** `record Message(id, taskId, event)`。
- **代码：** `Message`
- **坑：** 把消息当成数据库。队列不是持久账本，进程一停，内存队列里的消息就没了。真正要落库的仍然是 Task 本身。

### 1.5 Broker

- **是什么：** 管队列的中间人。Producer 和 Consumer 都不直接互相调用，只和 Broker 说话。
- **为什么需要：** 下游挂了、变慢了、以后再加一个审计消费者，创建任务的代码都不用改。
- **怎么做：** 本日的 `Broker` 就是一个包装了 `BlockingQueue` 的类。真实系统里这个角色是 RabbitMQ 进程，和业务进程分开。
- **代码：** `Broker#publish`、`Broker#take`
- **坑：** 把 Broker 写进业务进程里，只能演示解耦，不能扛进程崩溃。应用一退出，队列一起没。

### 1.6 同步 vs 异步

- **是什么：** 同步是调用方一直等到对方做完。异步是调用方把工作交出去就返回，结果以后才发生。
- **为什么需要：** 「创建任务」必须快且确定；「发通知」可以晚一点。绑在一起，通知变慢，创建接口就变慢。
- **怎么做：** `Day29App` 先直接 `consumer.handle(...)`，再 `producer.publishTaskCreated(...)`。后者只做 `offer`，所以等待时间接近 0，此时 `queue=1`，消息还在队列里，消费者线程随后才取走。
- **代码：** `Day29App#main` 的两段
- **坑：** 异步不等于「已经做完」。`accepted=true` 只表示进了队列，不表示通知已经发出。调用方如果这时告诉用户「邮件已发送」，就是说谎。

## 2. 代码导读

| 符号 | 职责 |
|---|---|
| `Message` | 一条任务事件，不承载 Task 的全部字段 |
| `Broker` | 本日的中间人，内部只有一个有界队列 |
| `TaskEventProducer#publishTaskCreated` | 生产 CREATED 事件 |
| `TaskEventConsumer#handle` | 消费并模拟慢通知 |
| `Day29App` 同步段 | 生产者直接调用消费者，等待约 400 ms |
| `Day29App` 异步段 | 生产者只 `publish`，先打印队列长度，再启动消费者 |

Spring 里以后会变成：`RabbitTemplate.convertAndSend` 对应 Producer，`@RabbitListener` 对应 Consumer，RabbitMQ 进程对应 Broker。那天再写，今天不接。

## 3. 与综合项目的关系

创建 Task 成功后，不在同一个请求里发通知、记审计。先写数据库，再投一条 `CREATED` 消息。通知失败不应该把「任务已创建」回滚掉；那是两条不同的成败。

## 4. 自测

1. 用自己的话区分 Producer、Consumer、Queue、Message、Broker。谁允许认识谁？
2. 创建任务后要发通知。如果同步调用通知，接口会怎样？改成异步投递后，`accepted=true` 能不能理解成「通知已发出」？
3. `Broker#publish` 里的 `queue.offer` 在做什么？返回 false 时消息在哪？

### 学员作答与批语（2026-09-21）

**第 1 问**

> 学员：生产者、消费者；通讯像邮箱，Queue 寄存 Message，Broker 像邮递公司，做中间件完成交换和寄存。

✅ **通过。** 邮箱比喻成立。补一条边界：Producer 和 Consumer **互不认识**，只认识 Broker。本日 Broker 只负责寄存和交出，还没有 RabbitMQ 那种按路由键转发；「交换」是 Day30 的 Exchange，先不要提前加给今天的 Broker。

**第 2 问**

> 学员：同步时是 Producer 直接调用消费者。不能。

✅ **「不能」通过。** 补前半句的后果：同步时创建任务的接口必须等 `handle` 里那 400 ms 通知做完才返回，通知一慢，创建接口一起变慢。`accepted=true` 只表示 `offer` 成功，消息还在队列里，通知还没发生。

**第 3 问**

> 学员：将消息插入队列，返回 false 表示队列已满。

✅ **通过。** 补位置：返回 false 时消息**不在队列里**，仍在调用方手里。调用方如果丢掉返回值，这条事件就丢了，而且没有任何报错。

**闸门结论：三问通过（第 1 问划清「寄存」和 Day30「交换」；第 2、3 问补了后果和消息位置），Day29 闭环。**
