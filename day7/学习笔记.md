## 1. 概念

### 1.1 ThreadPoolExecutor 与核心参数

- **是什么：** 复用固定范围工作线程执行提交的任务，实现 `ExecutorService`。
- **为什么需要：** 每个请求 `new Thread` 会耗尽内存/CPU；池化控制并发度。
- **怎么做：**

```text
corePoolSize=2      常驻线程
maximumPoolSize=4   队列满后可扩到的上限
workQueue           任务排队（本 Demo 容量 4）
keepAliveTime=30s   非核心线程空闲存活
rejectionPolicy     队列和最大线程都满时的策略
```

执行顺序（简化）：线程 &lt; core → 建线程；否则进队列；队列满且线程 &lt; max → 建非核心线程；再满 → 拒绝。

- **代码：** `Day7App` 构造 `ThreadPoolExecutor`
- **坑：** `Executors.newFixedThreadPool` 用无界队列，可能堆积 OOM；生产建议手写 ThreadPoolExecutor。
- **坑：** 忘记 `shutdown`，进程挂起。

### 1.2 BlockingQueue

- **是什么：** 阻塞队列，池用它缓冲待执行任务。
- **为什么需要：** 生产速度 &gt; 消费速度时暂存，而不是立刻开无线程。
- **怎么做：** `new LinkedBlockingQueue<>(4)` 有界。
- **代码：** `Day7App` 的 `queue`
- **坑：** 无界队列 + 固定 core → 永远不扩到 max（常见误配）。

### 1.3 拒绝策略 RejectedExecutionHandler

- **是什么：** 池和队列都满时的策略。AbortPolicy 抛 `RejectedExecutionException`；还有 CallerRuns、Discard、DiscardOldest。
- **为什么需要：** 超载时要有明确背压，而不是静默丢光或拖死机器。
- **怎么做：** 本 Demo `AbortPolicy`，狂 `execute` 统计 `rejected`
- **代码：** `Day7App` 的 `rejected=`
- **坑：** Discard 策略丢任务无声，任务平台会「丢单」。
- **坑：** CallerRuns 在调用线程跑任务，可能拖慢 HTTP 线程。

### 1.4 CompletableFuture

- **是什么：** 可组合的异步结果：`supplyAsync` → `thenApply` → `exceptionally`。
- **为什么需要：** 异步导入任务完成后转换结果、统一处理失败，避免回调地狱。
- **怎么做：** 指定自家 `Executor`（本 Demo 用同一个 pool），避免默认 `ForkJoinPool.commonPool()` 被占满。
- **代码：** `Day7App` 的 `cf=`
- **坑：** 默认公共池跑阻塞 IO 会堵其他异步任务。
- **坑：** 不 `get`/`join` 也不处理异常，失败被吞。

### 1.5 Spring 里怎么用（结论）

自定义 `ThreadPoolTaskExecutor` Bean；`@Async` 指定 executor 名。不要用无界队列的默认友好方法糊弄生产。

## 4. 自测（含第一周验收）

1. HashMap 为什么线程不安全？ConcurrentHashMap 怎么解决？
2. synchronized 和 Lock 有什么区别？（Day6/7 延伸：本周主用 synchronized；Lock 可 tryLock/打断，下阶段再深挖）
3. volatile 能保证什么？
4. ThreadPoolExecutor 有哪些核心参数？
5. 为什么不能无限创建线程？
6. CompletableFuture 如何实现异步任务？

### 参考答案

1. 并发写无同步会丢数据/坏结构；CHM 用并发安全的桶级协作与原子 API。
2. synchronized 是内置监视器，简单；Lock（如 ReentrantLock）更灵活（可中断、超时、公平），但要手动 unlock。
3. 可见性，不保证复合操作原子性。
4. core、max、keepAlive、workQueue、rejectionHandler（再加线程工厂）。
5. 内存、调度开销、上下文切换；最终拖垮机器。
6. `supplyAsync` 在 executor 跑供应商，链式 `thenApply`/`exceptionally` 组合结果。

五问结论：学了池化与背压；为了受控并发执行任务；不用就 OOM 或拒绝无策略；坑是无界队列、错误拒绝策略、公共 ForkJoin 池跑阻塞任务。

## 4.1 闸门三问：学员回答与批语（2026-09-07）

开课闸门：① 核心参数与提交顺序 ② 为何慎用 `Executors.newFixedThreadPool` / 有界 vs 无界 ③ 为何先 CF 再压测拒绝、Abort 满了怎样。

### 第 1 问：core / max / workQueue / 拒绝策略；提交后怎么走？

**学员回答：**

> corePoolSize 表示核心中常驻的默认存活线程数量，maximumPoolSize 表示线程池最大线程容量、后续加入的线程会被阻塞，workQueue 表示任务队列情况。一个任务被提交后，会先检查池中线程数是否小于 corePoolSize，若小于则创建线程，否则检查是否任务队列满，若没满则进队列，否则检查池中线程是否小于 maximumPoolSize，若没满则建立非核心线程，不然则通过 handler 设置的策略进行处理，我们这个学习项目是选择 AbortPolicy 来处理。

**导师批语：提交顺序基本正确；改两处用词。**

- **对的：** 先比 core → 再看队列 → 队列满再比 max 建非核心 → 再满走 handler；本 Demo 用 `AbortPolicy`。
- **改：** `maximumPoolSize` 是**工作线程数量上限**，不是「后续加入的线程会被阻塞」。满载时通常是**新任务被拒绝**（Abort 抛异常），或按其它策略处理，而不是把「线程」挂起排队。
- **改：** `workQueue` 是存放**待执行 Runnable** 的阻塞队列，不是抽象的「队列情况」。

本 Demo 参数：`core=2`，`max=4`，队列容量 `4`，`AbortPolicy`。

**评语：通过（记住「满了拒任务 / 按策略」，别说成「阻塞后续线程」）。**

### 第 2 问：为何慎用 `newFixedThreadPool`？有界 / 无界对扩到 max 的影响？

**学员回答：**

> 因为 Executor.newFixedThreadPool 来创建线程池容易创建无界队列，导致产生 OOM，如果还有其他隐患请帮我补充；有界队列和无界队列由于其数据结构一个是数组的固定结构，一个是链表的可变结构，因此可能后者会无限创建线程。

**导师批语：OOM 方向对；「无界 → 无限创建线程」说反了，必须改掉。**

**`Executors.newFixedThreadPool` 其它隐患（补充）：**

1. 内部用**近乎无界**的 `LinkedBlockingQueue`，任务堆积可把堆撑爆（OOM）——你已点到。
2. 队列几乎永远装得下 → **很难触发「队列满」→ 线程数常卡在 core，`maximumPoolSize` 形同虚设**。
3. 不便自定义拒绝策略、线程名（排障时一堆 `pool-1-thread-n`）。
4. 调用方仍要自己 `shutdown`，工厂方法本身不解决生命周期。

**有界 vs 无界（关键订正）：**

| | 有界队列（本 Demo 容量 4） | 无界队列 |
|---|---|---|
| 队列满了以后 | 才可能再建线程直到 max；再满 → 拒绝 | 任务一直进队列，**往往扩不到 max** |
| 主要风险 | 拒绝 / 调用方背压 | 队列无限涨 → **OOM**；不是无限建线程 |

所以：无界队列危险的是**任务堆在队列里**，不是「无限创建线程」。有界才是「能扩到 max、再满就拒绝」的常见生产配法。也和「数组 vs 链表」无必然关系——`LinkedBlockingQueue` 也可以 `new LinkedBlockingQueue<>(4)` 做成有界。

**评语：部分通过；删掉「无界会无限创建线程」，改记上表。**

**学员订正（2026-09-08）：**

> 无界队列会因为 newFixedThreadPool 将任务队列无限扩容，很难触发满队列条件，从而使 maximumPoolSize 参数失效，核心依旧按照 core 的数量处理线程，不进入下面的流程，从而产生 OOM 问题。

**订正后批语：正确。** 风险是**队列里任务堆爆堆**，线程数卡在 core，不是无限建线程。

**评语：第 2 问通过。**

### 第 3 问：为何先 CompletableFuture、再压测拒绝？Abort 满了怎样？

**导师原答要点：** Abort 在 max+队列满时抛 `RejectedExecutionException`；CF 与压测共用一池，先打满再 CF 会被拒。

**学员复述（2026-09-08）：**

> 先 CF 是因为如果这个方法也是往后续压测的池子中提交异步任务，如果先压测则会把线程和队列占满导致异步任务无法提交。

**批语：通过。** 补充半句：Abort 下「无法提交」= 抛 `RejectedExecutionException`，不是静默卡住。

**评语：第 3 问通过。**
