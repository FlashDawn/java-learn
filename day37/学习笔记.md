## 1. 概念

### 1.1 Service Registration（服务注册）

- **是什么**：服务实例启动时，把「服务名 + IP + 端口」上报给注册中心（Nacos）；下线或宕机时从注册表移除。
- **为什么需要**：Day36 的痛点——硬编码 `http://127.0.0.1:18090` 在实例换机器/扩容/重建时全部失效。注册后，实例的「在哪」变成动态信息，调用方不再关心。
- **怎么做**：classpath 加 `spring-cloud-starter-alibaba-nacos-discovery`，配 `spring.cloud.nacos.discovery.server-addr` + `spring.application.name`——**零代码**，启动自动注册。
- **代码**：`application.yml`（discovery.server-addr）、`application-user.yml`（name=user-service）
- **实证**：`GET /nacos/v1/ns/service/list` 返回 `["user-service","task-service","data-service"]`
- **坑**：`spring.application.name` 就是服务名，起错名（含下划线、大小写不一）会导致调用方按名找不到；命名约定：小写 + 中划线。

### 1.2 Service Discovery（服务发现）

- **是什么**：调用方凭「服务名」向注册中心查可用实例列表，再由负载均衡挑一个发起调用。
- **为什么需要**：发现 + 注册是同一个电话簿的两面——写入侧是注册，读取侧是发现。它消灭了调用链上所有的硬编码地址。
- **怎么做**：`@LoadBalanced` 注解 RestTemplate：拦截请求 → 把 host 部分当服务名 → 问 Nacos 要健康实例 → 按策略（默认轮询）选一个 → 替换成真实 IP:端口发请求。
- **代码**：`task/TaskServiceApplication.java`（`@LoadBalanced` Bean）、`task/TaskController.java`（`http://user-service/users/...`）
- **实证**：`GET 18091/tasks/1/detail` 返回任务 + owner（与 Day36 结果相同，但 URL 里没有一个 IP）
- **坑**：忘了加 `spring-cloud-starter-loadbalancer` 依赖时，`@LoadBalanced` 报 `No instances available`——Spring Cloud 2020+ 把 Ribbon 移除了，LB 要显式引。

### 1.3 Health Check（健康检查）

- **是什么**：注册中心持续确认实例「活着且能干活」，不健康的实例从可用列表剔除，不再分到流量。
- **为什么需要**：没有健康检查，实例宕机后注册表还留着它的地址，调用方持续把请求打进黑洞（直到 TCP 超时）。
- **怎么做**（Nacos 两种模式）：
  - **临时实例（默认）**：客户端每 5s 发心跳，Nacos 超过 15s 没收到就标不健康、30s 剔除。AP 模式——网络分区时宁可保留疑似存活的实例，保可用性；
  - **持久实例**：Nacos 主动探测（TCP/HTTP），实例不因心跳中断被删，适合数据库这类「不能随意摘」的注册项。CP 模式（Raft）。
- **代码**：无（机制由 starter 与 Nacos Server 自动完成）；可用 `GET /nacos/v1/ns/instance/list?serviceName=user-service` 观察 `healthy` 字段
- **坑**：临时实例 + 长 GC 停顿（>15s）会被误摘——JVM 调优差的服务在注册表上「抖动」，流量忽有忽无。

### 1.4 Configuration（配置中心）

- **是什么**：Nacos 的第二块能力（对照 Day12 的单机 Profile）：配置集中存储在 Nacos，服务启动拉取、运行期监听推送。
- **为什么需要**：20 个服务改同一个开关，逐台改文件重启是灾难；配置中心改一次，秒级推到所有实例。
- **怎么做**：
  - 服务侧：`spring.config.import=optional:nacos:data-service.yaml`，启动时把远程配置并入 Environment；
  - 热更新：Bean 加 `@RefreshScope`，Nacos 推送变更时 Spring 重建该 Bean、`@Value` 注入新值；
  - 发布侧：控制台或 OpenAPI `POST /nacos/v1/cs/configs`。
- **代码**：`application-data.yml`（config import）、`data/DataController.java`（`@RefreshScope` + `@Value`）
- **实证**：发布前 `app.message = 本地默认值` → `POST /nacos/v1/cs/configs` 发布 → **不重启**，再查变成 `来自Nacos配置中心的问候`
- **坑**：`@RefreshScope` 只重建加了注解的 Bean；把配置注进普通单例（如 `@ConfigurationProperties` 之外的常量字段）不会热更新。另外配置变更要进审计——生产上「谁改的、何时改的、上一版是什么」必须可追溯。

## 3. 生产环境注意事项

1. **Nacos 必须集群**：至少 3 节点（Raft 选主要奇数），前置 Nginx/SLB 做统一入口；单机 standalone 只能学习用。底层存储从嵌入式 Derby 换成 MySQL。
2. **命名空间隔离环境**：用 namespace 区分 dev/test/prod，group 区分业务线——不要把所有环境塞进 public。
3. **开启鉴权**：`NACOS_AUTH_ENABLE=true` + 改默认口令；本日学习关鉴权是为减少干扰项。
4. **保护阈值**：集群水位低时（健康实例比例 < 阈值），Nacos 把不健康实例也返回给调用方兜底——宁可打到可能挂的实例，也不整体无实例可用（防雪崩的反面思考）。
5. **配置发布灰度**：重要配置先在单个 group/灰度实例验证，再全量推。

### 参考答案与批语（2026-10-15 学员作答）

**1. 服务注册和服务发现分别发生在哪一侧？Nacos 里存的「电话簿」长什么样？**

学员作答：分别发生在：服务方和注册中心、注册中心和调用方之间。电话簿本质是服务的注册和调用地址

批语：✅ 两侧关系正确——注册是「服务方 ↔ 注册中心」的写入，发现是「调用方 ↔ 注册中心」的读取。电话簿的准确数据结构补全：**`服务名 → 实例列表`**，每个条目含 `IP + 端口 + 健康状态 + 权重 + 元数据`（可用 `GET /nacos/v1/ns/instance/list?serviceName=user-service` 看到实物）。注意健康状态也在里面——这就是为什么发现机制天然带「不派流量给挂掉的实例」。

**2. `@LoadBalanced` 做了什么？user-service 扩成 3 个实例，调用方代码要改吗？**

学员作答：拦截请求→ 把 host 部分当服务名 → 问 Nacos 要健康实例 → 按策略选实例 → 替换成真实 IP:端口发请求。不用，nacos可以推送到所有实例

批语：✅ 结论与机制链都对。把「不用改」的原理讲得更准一点：调用方本地维护一份**实例列表缓存**，它向 Nacos **订阅** user-service 的变更——新实例注册进来，Nacos 主动推送（gRPC）给所有订阅者，本地列表秒级更新，LoadBalancer 轮询时自然把新实例纳入轮换。全过程调用方代码零改动、零重启——这就是「弹性扩容」在微服务里的具体含义。对比 Day36：那时加实例要改代码+重发布，现在只要在 Nacos 里多一行注册记录。

**3. 热更新为什么需要 `@RefreshScope`？普通 `@Value` 字段为什么不自动变？**

学员作答：@RefreshScope 只重建加了注解的 Bean；把配置注进普通单例（如 @ConfigurationProperties 之外的常量字段）不会热更新

批语：✅ 结论正确（笔记 §1.4 的坑点）。往下钻一层「为什么」：`@Value` 注入发生在 **Bean 初始化那一刻**——构造完成后字段就固定了，之后 Environment 里的值再怎么变，也没有任何人回来重新给这个字段赋值。`@RefreshScope` 的魔法是给 Bean 包一层**代理**：配置变更事件到达时销毁旧实例、用新 Environment 重建一个，后续调用都被代理转发到新实例——所以新值「看起来」自动生效了。理解了这层就明白两个推论：① 没加注解的单例永远停在启动时的快照；② 重建有成本，热更新适合开关/阈值类配置，不适合高频变动的数据。

1. **user/task 服务启动失败：`No spring.config.import property has been defined`**（已修复）：`nacos-config` starter 在共享 classpath 上，Spring Cloud 默认强制每个服务声明 `spring.config.import=nacos:...`；本工程只有 data-service 用配置中心。修复：在共用 `application.yml` 里设 `spring.cloud.nacos.config.import-check.enabled=false`。教训：单工程多服务的结构里，starter 的强制检查会波及所有服务。
