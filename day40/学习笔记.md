## 1. 概念

### 1.1 ZNode（数据模型）

- **是什么**：ZK 的数据模型是一棵**类文件系统的树**，每个节点叫 ZNode——既能存少量数据（**≤1MB**），又能有子节点，是目录与文件的合体。每个 ZNode 自带 stat（版本号、事务 id、子节点数等）。
- **为什么需要**：分布式协调需要的不是数据库，而是一个**极小、极可靠、大家都能看**的共享黑板：配置、实例地址、「谁是 Leader」这类元数据往上一放，所有人读到同一份。1MB 限制是故意的——它逼你只放元数据。
- **怎么做**：四种类型（ZNodeDemo 逐一创建）：

| 类型 | 生命周期 | 命名 | 用途 |
|---|---|---|---|
| PERSISTENT 持久 | 显式 delete 才消失 | 原样 | 配置（`/day40/config`） |
| EPHEMERAL 临时 | **Session 死亡即自动删除** | 原样 | 服务实例注册（§1.2） |
| PERSISTENT_SEQUENTIAL 持久顺序 | 显式删 | 尾部追加 10 位单调序号 | 全局时序/队列 |
| EPHEMERAL_SEQUENTIAL 临时顺序 | Session 死即删 | 追加序号 | **选举与公平锁的原材料**（§1.4/§1.5） |

- **代码**：`ZNodeDemo.java`（实证：`/day40/task-0000000002`、`/day40/task-0000000003` 序号递增）
- **坑**：① 「顺序」是**每个父节点独立计数**的，不是全局计数器；② ZNode 不是拿来存业务数据的——把几 MB 的 JSON 塞进去会拖垮整个集群的写性能与快照同步。

### 1.2 Session（会话）

- **是什么**：客户端与 ZK 集群之间的逻辑会话，靠心跳维持，带 `sessionTimeout`。**临时节点的生命周期挂在 Session 上**——这是全课最重要的一个挂钩。
- **为什么需要**：服务发现要解决的核心问题是「实例死了，注册表怎么知道」。ZK 的答案很硬：**它不需要被通知**——实例宕机 → 心跳停 → Session 过期 → 该会话所有临时节点被服务端自动删除 → 订阅者收到 Watcher 通知。与 Day37 Nacos 临时实例的心跳剔除（15s 不健康 / 30s 剔除）是同一思想的不同实现。
- **怎么做（关键区分）**：**TCP 断开 ≠ Session 死亡**。网络抖动断开，只要在 sessionTimeout（本工程 10s）内重连，会话和临时节点都还在；真正死亡（超时或显式 close）才触发删除。这个设计防止「一次网络抖动就全网抖一遍注册表」。
- **代码**：`Zk.java`（sessionTimeoutMs=10s）、`SessionDemo.java`（实证：worker close 后实例列表从 `[worker-1]` 变 `[]`，全过程无任何「下线通知」）
- **坑**：**长 GC 停顿 > sessionTimeout 会被判死**——应用其实活着，但 ZK 已删光它的临时节点：服务被摘流量、锁被释放（§1.5 还会回来咬人）。JVM 调优差的服务会在注册表上「抖动」。sessionTimeout 别太短（误杀）也别太长（故障发现慢），10~30s 常见。

### 1.3 Watcher（变更推送）

- **是什么**：客户端对节点注册监听，节点变化时 ZK **主动推送**通知——免去轮询。协调的另一半：数据在树上（§1.1），变化靠 Watcher 送达。
- **为什么需要**：发现/协调的时效性全靠它。Consumer 轮询实例列表，间隔期内拿到的是旧名单；Watcher 让变更**秒级**推达（对照 Day37 Nacos 的 gRPC 推送——「订阅推送」是所有注册中心的共同语言）。
- **怎么做**：**原生 Watcher 是一次性的**——触发一次即自动注销，要持续监听必须重新注册。Curator 的 `NodeCache`/`TreeCache`/`PathChildrenCache` 封装了「自动重注册 + 本地缓存」，生产一律用封装。
- **代码**：`WatcherDemo.java`（实证：一次性 Watcher 收到 v2 变更后注销，v3 变更**无任何通知**；NodeCache 收齐 v4、v5 两次）
- **坑**：① 忘重注册 = 后续变更全丢，ZK 新手第一大坑；② **通知会合并**：变更快于投递时，多次变更只投一次、只看到最新值（WatcherDemo 初版连写 v4/v5 就合并了）——所以 Watcher 语义是「**可能有新变化，自己去读**」，不是「逐条变更日志」，读到通知后必须重新 getData 拿当前值；③ 羊群效应见 §1.5。

### 1.4 Leader / Follower / Quorum（集群机制）与 Leader Election（选举原语）

- **是什么（集群侧）**：ZK 集群（ZAB 协议，与 Raft 同族）里有且只有一个 **Leader**，其余为 **Follower**。所有**写**请求都经 Leader，过半 **Follower 确认（Quorum）** 才算提交；读请求 Follower 可直接响应。
- **为什么需要**：「过半」解决的是分布式系统的根本难题——**网络分区时两边都自称合法（脑裂）**。过半机制保证：任何时刻至多一方能凑够多数派，集群只有一个声音。这也是 ZK 集群**必须奇数台**的原因：3 台容忍挂 1 台（多数派 2）；4 台同样只容忍挂 1 台（多数派 3）——偶数台白花钱不增可靠性。
- **怎么做（应用侧选举）**：「在集群里选出一个干活的 Leader」是应用层需求（如只有 Leader 实例负责派发任务，避免重复派发）。用 ZK 原语手动实现：每个实例建 **EPHEMERAL_SEQUENTIAL** 节点，**序号最小者当选**；其余各 Watch **自己前一个序号的节点**——前任死亡才轮到自己继位。Curator 的 `LeaderLatch` 是这套算法的工业封装。
- **代码**：`LeaderElectionDemo.java`（实证：3 实例抢，worker-2 当选；**杀死 worker-2 的 Session** 后 worker-1 自动继位，全程无人工介入）
- **坑**：① 为什么 Watch 前驱而不是都 Watch 当选节点——防**羊群效应**：Leader 节点删除时若 1000 个候选者都被通知，1000 个客户端同时惊醒抢锁/抢位，ZK 瞬间被打爆；Watch 前驱则每次只唤醒一个人；② LeaderLatch 的 `isLeader()` 回调里别做阻塞长任务，会卡住选举线程；③ CP 的代价：分区时少数派**拒绝服务**（宁错杀不可用，不出错数据）——对照 Day37 Nacos AP 模式的取舍。

### 1.5 Distributed Lock（分布式锁）

- **是什么**：跨进程都认的互斥锁。JVM 内 `synchronized` 管不到别的进程（呼应 Day6：计数器在另一台机器手里时，本地锁毫无意义）。
- **为什么需要**：库存扣减、任务防重、选主互斥……分布式系统的「同一时刻只有一个干活」诉求无处不在。Day28 用 Redis 解（SET NX PX + Lua 释放），本日是第二种主流解法。
- **怎么做**：争抢者在锁路径下建 **EPHEMERAL_SEQUENTIAL** 节点，序号最小者持锁，其余 Watch 前驱排队。Curator `InterProcessMutex` 封装此算法（可重入）。
- **代码**：`DistributedLockDemo.java`（实证：10 线程×5 万读-改-写，无锁期望 500000 实得 **67554**（丢 43 万次更新）；ZK 锁保护下 10×1000 精确 **10000**）
- **与 Day28 Redis 锁对照**：

| | Redis 锁 | ZK 锁 |
|---|---|---|
| 争抢方式 | SET NX PX 抢占 + 自旋重试 | 建序号节点排队 + Watch 前驱等通知 |
| 公平性 | 无（谁抢到是谁） | **天然公平**（先来先得） |
| 持有凭证 | key 未过期 | **Session 存活** |
| 死锁防护 | TTL 兜底 | Session 死亡自动删节点 |
| 怕什么 | GC 长停顿 → TTL 过期 → 锁被抢 → 误删别人锁（RedLock 之争） | GC 长停顿 > sessionTimeout → Session 死 → **同样丢锁** |

- **坑**：① 结论很扎心：**两种锁都怕长 GC**——分布式锁解决互斥，解决不了「持有者假死」，临界区必须再配幂等/ fencing token 兜底；② ZK 锁的吞吐远低于 Redis 锁（每次 acquire 一次 ZK 写），超高频互斥场景选型时要想清楚；③ 本 Demo 还留了一个诚实的教学注脚：裸 `count++` 在现代 JIT 下竞态窗口太小，10×1000 可能侥幸不丢数据——**没观察到 bug 不代表 bug 不存在**，演示/压测要把剂量加到必然暴露。

## 3. 生产环境注意事项

1. **集群必须奇数台**（3 或 5），跨机房部署时保证任意单机房故障后剩余仍够多数派；3 台是性价比甜点（容忍 1 台）。
2. **ZK 是 CP 系统**：分区时少数派直接拒绝服务。注册中心选型对照——Eureka/Nacos 临时实例是 AP（分区时宁可给旧名单也不拒答），ZK 是 CP（宁可拒答不给可能错的名单）。**发现场景 AP 通常更香，锁/选主场景必须 CP**。
3. **别把 ZK 当数据库**：单节点 ≤1MB、写性能随集群规模下降（写要过半同步）。它只存元数据：配置、地址、锁、选主状态。
4. **防羊群**：任何「等某个节点变化」的场景，Watch 前驱/具体节点，不要一堆客户端 Watch 同一个热点节点；客户端数量大时这是生死线。
5. **sessionTimeout 与 JVM 调优联动**：长 GC 假死会被判死摘流量。生产上 G1/ZGC + 合理堆，别让 Full GC 超过 sessionTimeout。
6. **可选练习（串起 Day39）**：Dubbo 的传统注册中心就是 ZK——把 day39 的 `dubbo.registry.address` 改成 `zookeeper://127.0.0.1:2181`、依赖换成 `dubbo-registry-zookeeper` + curator，即可实证「同一份 Dubbo 契约，换一个注册中心实现」。本日为保持 day39 可运行状态未改动。
7. **重试策略**：学习期 `RetryOneTime` 够用；生产用 `ExponentialBackoffRetry`，防故障恢复瞬间的重试风暴。

### 参考答案与批语（2026-10-16 学员作答）

**1. 实例宕机后 ZK 如何得知并剔除？「TCP 断开」vs「Session 过期」的区别为何是题眼？**

学员作答：宕机后所有临时节点会被服务端自动删除，不做通知。因为 TCP 短暂断开不意味着 Session 死亡。

批语：✅ 核心正确。补两处精度：
- **链条补全**：实例宕机 → **心跳停止**（客户端靠定期心跳维持会话）→ 超过 `sessionTimeout` 未收到心跳 → ZK 判定 Session 过期 → 删除该会话所有临时节点。「如何得知」的答案就是「心跳 + 超时」——不需要任何智能检测。
- **「不做通知」要分两个方向说清**：实例→ZK 方向，确实不需要任何「下线通知」（这正是机制的美妙——对比需要主动注销、宕机就留脏数据的注册表）；但 ZK→订阅者方向，**会主动发 Watcher 通知**——Watch `/workers` 的 Consumer 秒级得知列表变了。记忆口诀：一「不」一「要」——**不要实例通知，要给订阅者通知**。
- TCP≠Session 的实务意义：**网络抖动不抖注册表**——抖动期内在 timeout 前重连，会话与临时节点原样保留；只有真死（超时）才触发剔除与通知。

**2. 监听 `/workers` 子节点列表忘了重注册会怎样？Curator 怎么解决？**

学员作答：相当于后续变更全丢，其余请补全。

批语：✅ 结论正确。补全业务后果与对应封装：
- **后果是两个方向的瞎**：① 新上线的实例永远看不到——**扩容白扩**，流量全堆在老实例上；② 已宕机的实例还以为活着——请求持续打进黑洞，直到 TCP 超时。这时候 Day38 的熔断器成了最后一道防线——**知识串起来了：注册发现的纰漏，最终靠调用链韧性兜底**。
- **Curator 三兄弟按监听范围选**：单节点数据用 `NodeCache`；**子节点列表（本题场景）用 `PathChildrenCache`**；整棵子树用 `TreeCache`。它们都封装了「自动重注册 + 本地缓存」。
- **正确姿势**：无论用不用封装，收到通知后的动作是**重新读当前全量**（`getChildren`）——Watcher 只说「可能变了」，不说「变成什么样」（§1.3 通知合并实证）。

**3. Watch 前驱 vs 全 Watch 锁节点解决了什么？GC 长停顿时 ZK 锁与 Redis 锁各自怎样？**

（学员要求导师详细回答，以下为标准答案）

- **解决的是羊群效应（herd effect）**：假设 1000 个等待者都 Watch 锁节点本身——锁释放瞬间，1000 个通知同时发出，1000 个客户端同时惊醒，都去查「我是不是最小序号」，999 个发现不是、白跑一趟。一次锁释放 = O(n) 通知 + O(n) 次查询风暴，ZK 直接被打爆；而且谁来抢凭运气，无公平性。Watch 前驱把锁变成**接力赛**：每次只唤醒**下一个排队者**一个人，O(1) 通知，且天然 **FIFO 公平**（先来先得）——对比 Day28 Redis 锁的自旋抢占，谁抢到凭运气，没有公平性可言。
- **GC 长停顿：两种锁都防不住（扎心但重要的结论）**：
  - **Redis 锁**：A 持锁中 GC 停顿 > TTL → key 过期 → B 拿到锁进临界区 → A 的 GC 回来**以为自己还持锁**，也进临界区 → **两个客户端同时在临界区，互斥破产**。A 最后执行释放时若没校验 value，还会误删 B 的锁（Day28 的 Lua 校验防的是这一刀，但 Lua 防不了「双进临界区」本身——这就是 RedLock 之争的核心）。
  - **ZK 锁**：A 持锁中 GC 停顿 > `sessionTimeout` → Session 过期 → 临时节点被删 → B（Watch 前驱被触发）拿到锁 → A 的 GC 回来同样以为自己还持锁 → **同样双进临界区**。
  - **工程解：fencing token**——锁服务给每次持有发一个**单调递增令牌**（ZK 的节点序号/zxid 天然可充当），资源侧（DB/存储）记录已见过的最大令牌，**拒绝携带旧令牌的写**——假死的 A 拿着过期令牌来写，被资源拒之门外。拿不到 fencing 的场景，退回业务幂等兜底（Day35 状态关口、Day39 唯一单号——同一条族谱第三次出现：**锁防并发，幂等防一切**）。

2. **无锁计数 10×1000 不丢数据的假象**（已修复）：裸 `count++` 竞态窗口太小，现代 JIT+多核下可能侥幸全对。修复：改成「读-yield-写」还原真实业务的读-改-写窗口 + 发令枪同时起跑 + 剂量加大到 50k/线程——期望 50 万实得 67554，病灶暴露。教训：**没观察到 bug 不代表 bug 不存在，实验设计要让小概率事件必然显形**。
3. **NodeCache 通知合并**（已修复）：连写 v4/v5 只收到一次通知（最新值 v5）。这正是 Watcher 语义「可能有变化，自己去读」的实证；Demo 加 500ms 间隔后两次收齐。
4. **华为云镜像无 zookeeper**（已绕行）：`swr.../library/zookeeper:3.9` not found；换 DaoCloud `m.daocloud.io/docker.io/library/zookeeper:3.9` 拉取后 `docker tag` 回官方名。
