## 1. 概念

### 1.1 Generic（泛型）

- **是什么：** 类型参数，编译期约束容器里装什么。
- **为什么需要：** 不用泛型的仓库只能装 `Object`，取出要强转，塞错类型运行时才爆。
- **怎么做：** `class Repo<T>`；`Repo<Task> repo = new Repo<>();`
- **代码：** `Repo.java`、`Day4App` 的 `Repo<Task>`
- **坑：** 泛型擦除：运行时没有 `T`；不能 `new T()`、不能 `T[].class` 乱来。
- **坑：** 原始类型 `Repo repo = ...` 丢掉保护，等于回到 Object。

### 1.2 Lambda 与函数式接口

- **是什么：** 函数式接口（只有一个抽象方法）可用 `->` 或方法引用写成短函数。
- **为什么需要：** Stream 的 filter/map 需要「一段行为」；匿名内部类太吵。
- **怎么做：** `task -> "CREATED".equals(task.getStatus())`；`Task::getId`
- **代码：** `Day4App` 的 `filter`、`map(Task::getId)`、`sorted((a,b)->...)`
- **坑：** Lambda 捕获的外部局部变量必须是 effectively final。
- **坑：** 在 Lambda 里改共享可变状态，和并行流一起会出竞态。

### 1.3 Stream

- **是什么：** 对集合做的声明式流水线：中间操作惰性，终端操作才触发计算。
- **为什么需要：** 任务列表的筛选、排序、分组、求和用循环又长又易错。
- **怎么做（对照计划）：**

| 操作 | 作用 | 本 Demo |
|---|---|---|
| filter | 留下满足条件的 | CREATED 任务 |
| map | 一对一变换 | Task → id |
| flatMap | 一对多再摊平 | type+status 列表摊平 |
| sorted | 排序 | 按 cost |
| collect | 收成集合/Map | toList、groupingBy |
| groupingBy | 按键分组 | 按 type |
| reduce | 聚合成一个值 | cost 求和 |

- **代码：** `Day4App.main` 整段 stream
- **坑：** 终端操作后流不能再用。
- **坑：** `parallelStream()` 默认公共池，IO 密集或阻塞任务别瞎并行。

### 1.4 Optional

- **是什么：** 可能有、可能没有的值的显式包装，逼你处理空。
- **为什么需要：** `get` 到 null 再解引用 → NPE；Optional 把「没有」变成类型的一部分。
- **怎么做：** `findFirst()` → `orElseGet(() -> ...)`；不要 `get()` 不判断。
- **代码：** `Day4App` 的 `missing=`
- **坑：** 不要把 Optional 当字段到处传；适合返回值。
- **坑：** `Optional.of(null)` 直接 NPE，应用 `ofNullable`。

### 1.5 Spring 里怎么用（结论）

Service 里用 Stream 做内存过滤/组装 DTO；持久层过滤仍交给 SQL。Optional 常作 repository `findById` 返回类型。

## 4. 自测

1. `Repo<Task>` 比 `Repo` 原始类型好在哪？
2. `map` 和 `flatMap` 的区别？
3. `Optional` 里找不到 t-9 时本 Demo 如何避免 NPE？

### 参考答案

1. 编译期阻止 `add` 错类型，取出不用强转。
2. map 一对一；flatMap 每个元素变成流再合并，用于摊平嵌套。
3. `orElseGet` 提供默认 Task，不调用可能为 empty 的暴力 `get()`。

五问结论：学了泛型与 Stream 流水线；为了类型安全与声明式处理任务列表；不用就强转+手写 for；坑是并行流滥用、Optional 误用、流用两次。
