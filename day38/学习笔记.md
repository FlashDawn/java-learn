## 1. 概念

### 1.1 Gateway（网关）

- **是什么**：系统的统一入口。所有外部请求先打到网关，网关按规则（Predicate）匹配后转发（Route）给后端服务，途中可插拔横切逻辑（Filter：鉴权/限流/日志）。
- **为什么需要**：没有网关时，前端要记 user-service 在 18100、task-service 在 18101……每加一个服务前端改一次。有了网关，**外部世界只需要知道 18099 一个地址**，内部服务怎么拆、怎么扩容都与外部无关。横切逻辑（鉴权、限流、跨域）也收敛到一处，不再每个服务重复写。
- **怎么做**：`spring-cloud-starter-gateway` + 配置路由。本工程的路由只有两条：

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: user-route
          uri: lb://user-service      # lb:// = 从 Nacos 发现实例 + 负载均衡选一个
          predicates:
            - Path=/users/**          # 路径匹配 /users/** 的转发给 user-service
        - id: task-route
          uri: lb://task-service
          predicates:
            - Path=/tasks/**
```

- **代码**：`gateway-service/src/main/resources/application.yml`
- **实证**：`GET 18099/users/1`（打到 user-service）、`GET 18099/tasks/1/detail`（打到 task-service，task 内部再 Feign 调 user）——全程浏览器只认识 18099。
- **坑**：**Gateway 是 WebFlux（Netty 异步）应用，与 Spring MVC 的 Tomcat 栈互斥**——同一个模块同时引 `spring-boot-starter-web` 和 `spring-cloud-starter-gateway` 会直接启动失败。这正是本工程从 Day37 的「单工程多 profile」升级为「多模块」的直接原因：Gateway 必须独占一个模块。

### 1.2 OpenFeign（声明式 RPC 客户端）

- **是什么**：用「接口 + 注解」描述一次远程调用，Feign 在运行期动态代理出实现。调用方的写法与调本地 Spring Bean 完全一样。
- **为什么需要**：对照 Day37 的 RestTemplate 写法——`restTemplate.getForObject("http://user-service/users/" + id, ...)`：URL 拼接、HTTP 方法、返回值类型全散落在业务代码里。Feign 把「调哪个服务的哪个接口」收敛成一个 Java 接口，**契约可读、可重构、可编译期检查**。
- **怎么做**：

```java
@FeignClient(name = "user-service")   // 服务名，走 Nacos 发现
public interface UserClient {
    @GetMapping("/users/{id}")        // 描述远程接口的形状
    Object getUser(@PathVariable("id") Long id);
}
```

调用侧就是 `userClient.getUser(ownerId)`——这一行背后是：动态代理 → 按服务名问 Nacos 要实例 → LoadBalancer 选一个 → 发 HTTP → 反序列化响应。
- **代码**：`task-service/.../UserClient.java`、`TaskController.java`（注入使用）
- **实证**：`GET 18099/tasks/1/detail` 返回聚合结果 `{"id":1,"title":"写周报","ownerId":1,"owner":{...张三...},"degraded":false}`——`owner` 字段就是 Feign 跨进程取回的。
- **坑**：**忘了引 `spring-cloud-starter-loadbalancer` 时，Feign 调用报 `No Feign Client for loadBalancing defined`**——`@FeignClient(name="user-service")` 里写的是逻辑服务名，必须有人在运行期把它翻译成真实 IP:端口，这个翻译官就是 LoadBalancer。Spring Cloud 2020+ 移除了 Ribbon，LB 要显式引。

### 1.3 Load Balancing（负载均衡）

- **是什么**：同一个服务有多个实例时，调用方按策略挑一个发起调用。Spring Cloud 默认策略是轮询（Round Robin）。
- **为什么需要**：单实例是容量与可用性的双重天花板。扩成 N 个实例后，必须有人决定「这次请求给谁」——这个决策点天然附在「服务发现拿到实例列表」之后。
- **怎么做**：本日 LB 出现在**两个位置**，用的是同一套 `spring-cloud-starter-loadbalancer`：
  1. **Gateway 侧**：`uri: lb://user-service`——网关转发前先从 Nacos 拿实例列表再选一个；
  2. **Feign 侧**：`@FeignClient(name="user-service")`——代理发 HTTP 前同样走一遍「服务名 → 实例列表 → 选一个」。
- **代码**：无独立代码（`lb://` 前缀 + `@FeignClient` 名字即是开关）；依赖 `spring-cloud-starter-loadbalancer`
- **实证**：本日只跑了单实例，LB 的「多实例轮换」未实操——但机制与 Day37 `@LoadBalanced` 完全相同（问 Nacos 要列表 → 缓存本地 → 订阅推送 → 轮询挑选）。
- **坑**：LB 用的是**本地缓存的实例列表**，Nacos 推送有秒级延迟——实例刚下线的一小窗口内仍可能被打到，靠重试/熔断兜底（这正是 §1.4 存在的理由之一）。

### 1.4 Circuit Breaker（熔断器）

- **是什么**：调用下游失败率越过阈值时，熔断器「跳闸」（OPEN），后续请求**不再真发**，直接走降级逻辑（fallback）；过一段冷静期放少量试探请求（HALF_OPEN），成功则「合闸」（CLOSED）恢复。三种状态：`CLOSED → OPEN → HALF_OPEN → CLOSED`。
- **为什么需要**：下游挂了之后，每个请求都傻等超时（几秒）才把失败传回去——线程池迅速被占满，**一个服务的故障顺着调用链拖垮整个系统（雪崩）**。熔断器把「持续失败的调用」变成「快速失败 + 降级响应」，给下游恢复的时间，也保住自己的核心链路。
- **怎么做**（Resilience4j）：

```java
@GetMapping("/tasks/{id}/detail")
@CircuitBreaker(name = "userQuery", fallbackMethod = "detailFallback")
public Object detail(@PathVariable Long id) {
    Object owner = userClient.getUser(...);   // 这行失败率超标 → 熔断器 OPEN
    ...
}

// 降级方法：签名 = 原方法参数 + Throwable 收尾
public Object detailFallback(Long id, Throwable t) {
    // 返回「够用但不完整」的响应：任务本体还在，owner 标注已降级
    detail.put("owner", Map.of("degraded", true, "reason", "user-service 不可用，已降级"));
    ...
}
```

- **代码**：`task-service/.../TaskController.java`（`detail` + `detailFallback`）
- **实证**：正常时 `GET 18099/tasks/1/detail` 返回 `"degraded":false`；**停掉 user-service 后**再访问 → 返回 `"degraded":true` + `"reason":"user-service 不可用，已降级"`——接口 200 而非 500，任务本体照常可见。
- **坑（本日最值钱的一则排障）**：**`@CircuitBreaker` 注解静默失效**——停掉 user-service 后接口直接 500，fallback 根本没被调用。原因：Resilience4j 的注解靠 **AOP 切面**织入，而 task-service 的 pom 缺 `spring-boot-starter-aop`——没有 AOP，注解就是一行注释，**不报错、不警告、纯静默**。补上依赖后降级立刻生效。教训：凡注解式能力（`@Transactional`、`@Cacheable`、`@CircuitBreaker`）失效，先查切面依赖在不在。

## 3. 生产环境注意事项

1. **网关是咽喉，必须集群**：Gateway 本身挂了就全站不可达——至少双实例 + 前置 LB（Nginx/SLB）。网关层要极致轻薄：不做业务、不查库，只做路由与横切。
2. **Filter 链是双刃剑**：鉴权/限流/日志都往网关塞，链条一长延迟就涨。按「越重越靠后」排序，最重的（如鉴权查库）尽量异步化或缓存化。
3. **熔断参数要按业务调**：Resilience4j 默认「50% 失败率、滑动窗口 100 次」对低流量接口太钝——低流量接口改「基于计数的窗口（如 10 次）+ 慢调用比例熔断」。fallback 里返回的数据要有降级标记（如本日的 `degraded:true`），让前端/监控能区分「正常数据」与「兜底数据」。
4. **降级不是万能的**：查类接口可降级（返回缓存/兜底），写类接口慎用——写操作降级往往意味着丢数据，通常应该直接失败。
5. **Feign 超时必须显式配**：默认超时时长在很多版本里偏长，下游慢的时候网关线程会被拖死。生产上 connect/read timeout、重试次数都要按接口 SLA 显式声明。

### 参考答案与批语（2026-10-16 学员作答）

**1. `lb://` 前缀做了什么？写成 `http://127.0.0.1:18100` 会怎样？**

学员作答：用于翻译服务名到真实端口，从 Nacos 发现实例 + 负载均衡选一个；写死后会只认 18100 端口，不会根据实际启动端口智能选择。

批语：✅ 核心正确。「只认 18100」往后再推三层，才是硬编码的完整代价：
- **失去弹性**：实例换机器、换端口、扩缩容，网关配置全要改——回到 Day36 的痛点；
- **失去负载均衡**：user-service 扩成 3 个实例，请求也永远只打 18100 这一台；
- **失去健康剔除**：18100 挂了，网关照样把请求往黑洞里转发（直到超时），没有任何机制把它摘出来。

补一个实现细节：`lb://` 的翻译动作由 Gateway 的全局过滤器 **`ReactiveLoadBalancerClientFilter`** 完成——它识别 `lb` 这个 scheme，把后面的服务名交给 LoadBalancer 查实例列表、选一个，然后把请求 URI 重写成真实地址再转发。另外说明：写死地址不是绝对错误——调**外部第三方系统**时（人家不在你的注册中心里）只能写死；它只对**内部微服务**是反模式。

**2. 「服务名 → IP:端口」的翻译发生在哪两个位置？是不是同一套机制？**

学员作答：发生在 Gateway 和 Feign 侧；机制不一样，详细请补全。

批语：⚠️ **位置判断正确，机制判断错误**——订正：**是同一套机制**。两边底层都是 `spring-cloud-loadbalancer`，实例列表都来自同一个 `NacosServiceInstanceListSupplier`（订阅 Nacos + 本地缓存 + 推送更新），选择策略都是默认的 `RoundRobinLoadBalancer`。一个铁证就在 pom 里：**只引了一个 `spring-cloud-starter-loadbalancer`，Gateway 和 Feign 两边就都活了**——如果是两套机制，应该需要两个依赖。

「不一样」的只是**接入位置**（两个不同的拨号人，用同一个电话簿）：

| | Gateway 侧 | Feign 侧 |
|---|---|---|
| 触发点 | 全局过滤器 `ReactiveLoadBalancerClientFilter` | `FeignBlockingLoadBalancerClient` |
| 识别依据 | URI 的 `lb://` scheme | `@FeignClient(name="user-service")` 的名字 |
| 之后 | 重写 URI → Netty 转发 | 拼出真实 URL → 发 HTTP |
| 查列表/选实例 | **同一个 LoadBalancer，同一份 Nacos 缓存列表** | |

记住这个判断方法：**怀疑「两套机制」时，先看依赖树——同一个 starter 供出来的能力，机制就是同一套**。

**3. 熔断器三态如何流转？为什么说它双向保护？**

学员作答：失败率越阈值 → 跳闸 OPEN → 请求不再真发、直接走 fallback；冷静期后 HALF_OPEN 放试探请求，成功则合闸 CLOSED。熔断把「持续失败」变成「快速失败 + 降级响应」，给下游恢复时间，也保住自己的核心链路。

批语：✅ 状态流转与双向保护都说对了。补三个「从会背到会用」的细节：
- **流转的量化条件**：CLOSED→OPEN 不是「一次失败就跳」，而是**滑动窗口内**失败率（或慢调用比例）越阈值、且窗口内调用数达到最小样本量（防低流量误判）；OPEN→HALF_OPEN 靠 `waitDurationInOpenState`（默认 60s）到期自动转；HALF_OPEN 只放**有限几个**试探请求，达标合闸、不达标再跳闸。
- **「保护调用方」的深层**：不只是单次请求不傻等——是防止**线程池/连接池被慢调用占满**，故障顺着调用链向上传导（雪崩）。熔断的本质是「把故障隔离在下游」。
- **「保护被调方」的深层**：过载的下游最怕的不是持续流量，而是**恢复瞬间被打爆**（所有堆积的调用方同时重试，retry storm）。HALF_OPEN 的渐进式放流正是流量整形——这和 Day35 MQ 的「重试 3 次进 DLQ」是同一族谱：同步链路用熔断兜底，异步链路用重试+DLQ 兜底。

## 5. 故障清单

1. **Feign 调用报 `No Feign Client for loadBalancing defined`**（已修复）：task-service 缺 `spring-cloud-starter-loadbalancer`。`@FeignClient(name="user-service")` 写的是逻辑服务名，运行期必须由 LoadBalancer 翻译成真实地址；Spring Cloud 2020+ 移除 Ribbon 后，LB 要显式引。教训：`lb://` 与 `@FeignClient(name=...)` 都依赖 LB starter，缺了它注解能编译、启动不报、一调就炸。
2. **`@CircuitBreaker` 注解静默失效，停掉 user-service 直接 500 无降级**（已修复）：Resilience4j 注解靠 Spring AOP 织入，task-service 缺 `spring-boot-starter-aop`——没有切面，注解等于注释，**零报错零警告**。补上依赖后 fallback 生效。教训：注解式能力失效先查三样——切面依赖、代理模式（自调用）、Bean 是否由 Spring 管理。
