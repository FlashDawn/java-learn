## 1. Redis 是什么、为什么快

### 1.1 概念

可以把 Redis 想成：**远程的、超快的、带丰富数据结构的内存库**。

- 客户端发命令（`GET` / `HSET` / `LPOP`…）→ Redis 在内存里改数据结构 → 返回结果。
- 它不是「只能 `SET key value` 的缓存」；六种（及更多）结构对应不同访问模式。
- 和 Java `HashMap` 的差别：独立进程、可网络共享、可选持久化、有过期/淘汰、有原子命令与复制等高可用能力（后几天再学）。

在综合项目里的位置：

```text
用户/API → Task Service → 常先问 Redis（状态/用户缓存）
                         → miss 再问 PostgreSQL（Day24 Cache Aside）
```

### 1.2 为什么需要它

| 场景 | 不用 Redis | 用 Redis |
|---|---|---|
| 高频读任务状态 | 每次 SQL，DB CPU/连接打满 | 内存 GET，毫秒内 |
| 简易排队 | 自己用 DB `SELECT FOR UPDATE` 抢任务，难且慢 | List/Stream 弹出 |
| 排行/优先级 | `ORDER BY` 反复扫表 | ZSet 按 score |
| 分布式协作 | 多机内存各自一份对不齐 | 共享一份 Redis |

不用会怎样：热点全打主库，延迟抖、扩容贵；多 Worker 抢同一 Task 也更难（锁在 Day25）。

### 1.3 工作原理：为什么快（计划四问）

**（1）内存数据库**

- 读写主路径在 RAM，比磁盘随机 IO 快几个数量级。
- 仍可 RDB/AOF 落盘防宕机丢数据——那是持久化路径，**不改变「热路径在内存」**。今天先会用，持久化细节可后补。

**（2）单线程模型的历史原因**

- 早期设计：命令执行单线程 → 无锁、无竞态、实现简单。
- 内存操作本身极快，瓶颈常在网络；单线程足够撑很高 QPS。
- **注意：** 「单线程」指**执行命令**的主线程；不是「整个 Redis 只有一个线程」（还有生物钟、懒删除等辅助线程）。
- Redis 6+：**I/O 线程**可并行读请求/写响应，但**命令执行仍基本串行**——避免你以为「开了多线程就能并行跑两个慢 Lua」。

**（3）I/O Multiplexing（多路复用）**

```text
很多客户端连接
      ↓
事件循环（epoll 等）同时监听：谁可读、谁可写
      ↓
有事件才处理 → 读命令 →（主线程）执行 → 写回包
```

对比：一连接一线程会在高并发下炸线程；多路复用用少量线程伺候海量空闲连接。

**（4）快的另一半：高效数据结构 + 简单命令**

- 例如短 String、小 Hash 用紧凑编码；命令语义简单（一次往返做完一件事）。
- **慢命令会拖垮整个实例**（单线程执行）：`KEYS *`、对超大 key 做全量操作——这是生产最大忌讳之一。

### 1.4 常见错误 / 生产注意（与「快」相关）

- 把 Redis 当无限磁盘 → 内存满触发淘汰或 OOM。
- 用 `KEYS` 扫生产 → 阻塞主线程。
- 一个巨大 String/List/Hash（大 key）→ 一次网络与执行都变慢，主线程被占。
- 热 key 打满单分片 → 集群也救不了「一个 key」的瓶颈（后续再谈）。

## 2. 六种数据结构（展开）

统一 key 命名建议：`业务:实体Id:含义`，如 `task:t-1:status`、`user:u-1`。

### 2.1 String

- **是什么：** 最基本的 KV；值是二进制安全字符串（也可存整数做计数）。
- **为什么需要：** 状态开关、验证码、分布式锁雏形（Day25 `SET NX EX`）、简单缓存整段 JSON。
- **怎么做：** `SET` / `GET`；可 `INCR`、`EXPIRE`。
- **代码：** `Day22App` 中 `task:t-1:status`
- **坑：** 所有对象都塞一个大 JSON String → 改一个字段要读写整包；字段级更新更适合 Hash。
- **坑：** 无 TTL 的缓存 key 堆积占内存。

### 2.2 Hash

- **是什么：** 一个 key 下多个 field→value（像精简版对象）。
- **为什么需要：** User 的 `name`/`email` 可 `HGET` 单字段，不必解析整段 JSON。
- **怎么做：** `HSET` / `HGET` / `HGETALL`（字段多时慎用 ALL）。
- **代码：** `user:u-1`
- **坑：** `HGETALL` 超大 Hash = 慢命令风险。
- **坑：** 和 String 缓存同一用户两份数据，更新漏了一处会不一致（Cache 设计 Day24）。

### 2.3 List

- **是什么：** 有序、可重复的列表，两端插入弹出。
- **为什么需要：** 简易 FIFO/栈、时间线；Demo 里当任务队列。
- **怎么做：** `RPUSH` 入队 + `LPOP` 出队（或反过来约定）。
- **代码：** `queue:tasks`
- **坑：** 没有消费确认；进程弹出后崩溃 = 任务丢失。可靠场景看 Stream 或 MQ（Week5）。
- **坑：** `LRANGE 0 -1` 拉全量超大 List → 阻塞。

### 2.4 Set

- **是什么：** 无序、元素唯一。
- **为什么需要：** 标签、去重、共同好友（交集并集差集）。
- **怎么做：** `SADD` / `SMEMBERS` / `SCARD`；`SADD` 重复元素无效。
- **代码：** `task:t-1:tags`（`import` 加两次，`SCARD` 仍为 2）
- **坑：** 超大 Set 做 `SMEMBERS` 全量取出危险；用扫描类命令。
- **坑：** 需要排序时该用 ZSet，不要自己把 Set 拉回 Java 排序。

### 2.5 ZSet（Sorted Set）

- **是什么：** 每个成员带一个 score；按 score 排序。
- **为什么需要：** 排行榜、优先级队列、延时队列雏形（score=时间戳）。
- **怎么做：** `ZADD`；`ZREVRANGE` 取最高分；`ZRANGEBYSCORE` 按区间。
- **代码：** `board:priority`，score 越大越优先，Demo 取 top1 → `t-1`
- **坑：** score 设计错误（同优先级大量碰撞）导致业务次序不符合预期。
- **坑：** 成员名重复时会更新 score，不是新增两条。

### 2.6 Stream

- **是什么：** 追加写的消息/事件日志，每条有 ID；支持消费组（进阶）。
- **为什么需要：** 任务状态变更审计、比 List 更适合「可回放/多消费者」的事件流。
- **怎么做：** `XADD` 追加；消费用 `XREAD` / 消费组（今天只演示写入）。
- **代码：** `stream:task-events`
- **坑：** 只 `XADD` 不消费 → 内存涨。
- **坑：** 和 RabbitMQ/RocketMQ 职责重叠时要选型（Week5）；Stream 适合轻量事件，重业务投递常用专业 MQ。

### 2.7 怎么选（一张图）

```text
只要一个值 / 计数 / 锁雏形     → String
对象多个字段常改其一           → Hash
纯顺序排队且可接受偶发丢       → List（认真可靠 → Stream/MQ）
去重集合 / 关系              → Set
要排序、打分、延时            → ZSet
事件日志、可多消费者          → Stream
```

## 5.2 展开：「不用 Redis」到底会怎样？（第 2 问第二小问）

用任务平台的一个具体画面说明，不堆术语。

### 场景

假设上线后每秒有很多请求来问：

```text
GET /tasks/t-1     → 只要知道状态是不是 RUNNING
GET /users/u-1     → 只要显示用户名
```

这些数据其实**几秒内几乎不变**，但请求非常多——这叫**热点读**。

### 路径 A：没有 Redis（每次都打 PostgreSQL）

```text
请求1 → Task Service → SQL: SELECT status FROM task WHERE id='t-1'
请求2 → Task Service → 又一次同样的 SQL
请求3 → … 每秒成百上千次同样的 SQL
```

会发生什么：

1. **主库（PostgreSQL）被热点打满**  
   连接池占满、CPU 忙着重复查同一行。真正写库的业务（创建任务、改状态）也要排队，整站变慢。

2. **延迟抖**  
   库空闲时一次 SQL 可能 1～5ms；一挤就变成几十、上百 ms，甚至超时。用户感觉是「有时快有时卡」，即延迟抖动。

3. **扩容贵**  
   为了扛读，你可能把数据库垂直升级（更大机器）或上只读副本。数据库扩容贵、慢，而且只读副本还有复制延迟。  
   多数热点读其实不需要「事务级」的强一致到毫秒，用内存缓存挡一层往往更划算。

### 路径 B：有 Redis（热点先命中内存）

```text
请求 → Task Service → GET task:t-1:status（内存，通常亚毫秒～1ms 级）
                         ↓ 只有 miss 时才
                       SQL 查库，再写回 Redis（Day24 Cache Aside）
```

大部分请求在 Redis 结束，**主库只吃「缓存没有」或「写操作」**，压力 hump 被削平，延迟更稳，也不必仅为热点读去砸数据库规格。

### 和「跨实例」的关系（补充一句）

Task Service 若部署 3 个副本，各 JVM 里自己 `HashMap` 缓存会对不齐。Redis 是**进程外共享的一层**，三台机器看到同一份 `task:t-1:status`。这是「不用 Redis、只靠本机内存」也解决不好的点。

### 一句话收束

> **不用 Redis ≠ 系统不能跑**；而是在**读多、热点集中**时，用更贵、更易抖的数据库去扛本该用内存挡掉的流量。Redis 是把「重复的热读」从主库挪走。

（写多、必须强一致落库的路径仍然走 PostgreSQL；缓存如何与 DB 同步是 Day24。）

## 7. 环境启动记录（本机 Redis）

学员询问如何启动；本机当时无 `redis-cli` / Docker / 可用 WSL。结论已写入 `day22/README.md`，要点：

1. **推荐** Docker Desktop → `docker run -d --name redis22 -p 6379:6379 redis:7-alpine` → `docker exec -it redis22 redis-cli PING` 应回 `PONG`。
2. 然后：`cd day22 && mvn -q -DskipTests compile exec:java`。
3. **不要**用 winget 旧包 `Redis.Redis`（3.0）：无 Stream，`Day22App` 会失败。
4. 备选：WSL2 Ubuntu 装 `redis-server`，或 Memurai Developer（Windows 原生）。
