## 1. 概念

### 1.1 Monolith vs Microservice

- **是什么**：
  - **单体（Monolith）**：所有功能（User/Task/Order/消息/缓存）打包在一个进程里部署，Day14 的项目就是单体。
  - **微服务（Microservice）**：按业务域拆成多个独立进程，各自开发、部署、扩容，通过网络通信协作。本日把 User 和 Task 拆成两个服务就是最小实例。
- **为什么需要（拆分动机）**：
  1. **独立部署**：改 Task 逻辑不用整个系统重新发布；
  2. **独立扩容**：User 查询量大就只扩 user-service 实例，不浪费资源在 Task 上；
  3. **团队自治**：小团队负责小服务，代码库和认知负担都小；
  4. **故障隔离**：Task 服务挂了，User 查询还活着。
- **代价（不用会怎样 / 滥用会怎样）**：本地方法调用变成网络调用（延迟 + 失败模式）；分布式事务没了（Day35 的 MQ 最终一致性是解法之一）；运维对象从 1 个变 N 个。**团队小、业务简单时上微服务是纯亏**——单体 + 清晰模块边界（模块化单体）往往是更优解。
- **代码**：`user/UserServiceApplication.java`、`task/TaskServiceApplication.java`（两个独立进程）
- **坑**：拆分按**业务域**（DDD 限界上下文），不按技术层（把 Controller/Service/Dao 拆成三个服务是灾难）。

### 1.2 服务拆分

- **怎么做**：按业务域垂直切——user-service 管 User 域，task-service 管 Task 域；每个服务**私有数据**（学习阶段各用各的内存 Map，生产是各自的数据库，Database per Service），对外只暴露契约接口（HTTP API）。
- **关键纪律**：别的服务**不许直连你的数据库**，只能走你的 API——否则拆了个寂寞，改表结构还是牵一发动全身。
- **代码**：`user/UserController.java`（契约即边界）
- **坑**：共享数据库是最常见的「假微服务」反模式：进程分开了，数据还耦在一起。

### 1.3 服务间通信

- **是什么**：拆分后协作的两条路——
  - **同步**：REST/HTTP（本 Demo）、gRPC（高性能、强契约）。调用方阻塞等结果，简单直观，但产生**级联故障**风险（对端慢 → 自己线程池耗尽 → 自己也慢）；
  - **异步**：消息队列（Day29–35 刚学过）。解耦 + 削峰，但链路变长、排查变难。
- **实测**：`TaskController.detail` 用 RestTemplate 调 `http://127.0.0.1:18090/users/1`，把 owner 拼进任务视图。单体里这是一句 `userRepository.findById()`，微服务里变成一次网络往返。
- **选型经验**：查询聚合类用同步（用户等着看结果）；命令/事件类用异步（创建任务后通知 Worker，Day35 已经做过）。
- **坑**：同步调用必须设**超时**（RestTemplate 默认无超时，对端挂死会拖死自己），生产还要熔断（Resilience4j，后续周学）。

### 1.4 服务发现

- **是什么**：服务实例的「电话簿」。实例启动时注册自己的地址（IP:端口），调用方从电话簿查可用实例，而不是写死地址。
- **为什么需要**：本 Demo 的 `USER_SERVICE_URL = "http://127.0.0.1:18090"` 是**痛点实证**——user-service 换机器、换端口、扩成 3 个实例，task-service 全部抓瞎。云环境实例随时生灭，硬编码根本活不下去。
- **怎么做**：注册中心（Nacos/Eureka/Consul）维护「服务名 → 实例列表」；两种发现模式：
  - **客户端发现**：调用方从注册中心拉实例列表，自己选一个调（Spring Cloud LoadBalancer + Nacos，Day37 实操）；
  - **服务端发现**：调用方只找 LB（如 K8s Service），LB 负责挑实例。
- **坑**：注册中心本身是高可用要点——它挂了新实例注册不上、列表不更新；生产注册中心必须集群部署。

### 1.5 配置中心

- **是什么**：把散落在各服务 `application.yml` 里的配置集中管理（Nacos Config / Apollo），支持改配置不重启（热更新）、按环境（dev/test/prod）隔离。
- **为什么需要**：20 个服务改一个数据库地址，逐台改配置 + 重启是运维噩梦；配置中心改一次、全量推送。Day12 学的 `spring.config` + Profile 是单服务版的答案，配置中心是集群版。
- **怎么做**：服务启动时从配置中心拉配置（bootstrap 阶段），监听变更事件刷新。
- **坑**：配置中心不可用时服务要有**本地缓存/快照**兜底，否则配置中心一挂全站起不来。

### 1.6 负载均衡

- **是什么**：同一个服务有 N 个实例，流量怎么分。
- **怎么做**：
  - **客户端 LB**：调用方拿到实例列表后自己按策略选（轮询/随机/权重）——Spring Cloud LoadBalancer，无中间跳、少一层开销；
  - **服务端 LB**：独立 LB 层统一分发（Nginx、云厂商 SLB、K8s Service）——对调用方透明，但多一跳且 LB 自身要 HA。
- **与服务发现的关系**：发现回答「有哪些实例」，LB 回答「这次选哪个」——客户端模式下两者常在同一个组件里（LoadBalancer 从注册中心拿列表再选）。
- **坑**：轮询策略在实例性能不均时会把慢实例压垮；权重/最少连接策略更适合异构机器。

### 参考答案与批语（2026-10-10 学员作答）

**1. 用一句话分别定义单体和微服务；什么时候不应该拆微服务？**

学员作答：单体是所有功能被打包在同一个程序里，部署时均出现在统一进程；微服务则是将一个完整业务按照一定规则拆分成多块。业务简单时不要拆分

批语：✅ 定义准确（「同一进程」是单体的本质，「按规则拆分」点到了按域拆）。「业务简单不拆」对，再补一条同等重要的：**团队小也不拆**——微服务把复杂度从代码转移到运维（N 个进程的部署、监控、排查），三五人的团队扛不住这份运维税，模块化单体才是正解。规则即 §1.2 的业务域（限界上下文）。

**2. 为什么「共享数据库」是假微服务？正确做法是什么？**

学员作答：因为数据仍然耦合，正确的做法是让数据也划分业务域

批语：✅ 一针见血。补一句让它更具体：共享库意味着改一张表结构，所有连这个库的服务都得跟着改、跟着发——**进程拆了，发布节奏还绑在一起**，拆分的核心收益（独立部署）归零。正确做法即 **Database per Service**：每个服务私有自己的库（或至少私有 schema），跨服务取数只能走对方 API 或 MQ 事件，绝不直连。

**3. `USER_SERVICE_URL` 硬编码有什么害处？服务发现怎么解决？**

学员作答：不清楚，请你解释

批语：（导师代答）害处有三个层次：
① **地址变了就断**：user-service 换机器/换端口，task-service 所有调用立即失败，改代码重新发布才能恢复；
② **无法扩容**：user-service 扩成 3 个实例分担流量，硬编码只会盯着写死的那一个打，其余两个闲置；
③ **云环境根本活不下去**：容器实例随时被调度重建，IP 是临时的，没有永远正确的地址可写。
服务发现的解法（对照 §1.4）：引入**注册中心**当「电话簿」——user-service 每个实例启动时向 Nacos 注册「我叫 user-service，我在 10.0.0.5:18090」；task-service 不再记地址，只记**服务名**，调用前问 Nacos「user-service 现在有哪些实例」，拿到列表后由负载均衡选一个调。实例生灭 → 注册表实时更新 → 调用方永远拿到最新可用列表。这就是 Day37 要动手做的事。
