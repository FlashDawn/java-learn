## 1. 概念

### 1.1 Image（镜像）

- **是什么：** 只读的「应用打包模板」，由一层层只读层（layer）叠成。
- **类比：** 类（class）与对象的关系——镜像是类，容器是实例。
- **关键事实：** 两个镜像名可以指向同一个镜像 ID（本机 `redis:7-alpine` 与 `docker.m.daocloud.io/library/redis:7-alpine` 同 ID `ff02b58f971e`），这就是 `docker tag` 的本质：起别名，不复制数据。

### 1.2 Container（容器）

- **是什么：** 镜像跑起来的进程实例 = 镜像只读层 + 顶部一层可写薄层。
- **隔离原理（Linux 内核提供）：**
  - `namespace`：隔离进程、网络、文件系统挂载点、主机名等；
  - `cgroups`：限制 CPU / 内存用量。
- **本质认知：** 容器不是轻量虚拟机，是**被内核隔离和限额的普通进程**。Windows 上跑 Linux 容器，本质是 Docker Desktop 在 WSL2 里起了一个 Linux 虚拟机。

### 1.3 Dockerfile

- **是什么：** 描述「如何构建镜像」的文本配方。
- **当日实例：**

```dockerfile
FROM alpine:3.20
COPY hello.txt /app/hello.txt
CMD ["cat", "/app/hello.txt"]
```

- **要点：**
  - 每条指令产生一个新只读层 → 层可被缓存复用（改动前的指令不重跑）；
  - `CMD` 是容器默认启动命令，可被 `docker run 镜像 新命令` 覆盖；
  - `COPY` 把构建上下文里的文件打进镜像（与 Volume 的「运行时挂载」完全不同）。

### 1.4 Volume（卷）

- **是什么：** 由 Docker 管理的持久化目录，生命周期独立于容器。
- **为什么需要：** 容器删了可写层就没了；数据库类应用的数据必须活在容器外。
- **当日实测：**

```powershell
docker volume create day46-data
docker run --rm -v day46-data:/data alpine:3.20 sh -c "echo 'written by container A' > /data/msg.txt"
docker run --rm -v day46-data:/data alpine:3.20 sh -c "cat /data/msg.txt"
# 输出：written by container A  ← 容器 A 已删，数据还在，被容器 B 读到
```

- **两种挂载：** `-v 卷名:/路径`（命名卷，推荐）vs `-v 主机目录:/路径`（bind mount，开发调试用）。

### 1.5 Network（网络）

- **是什么：** 容器间的虚拟网络。默认 `bridge`，自建网络自带 **DNS 按容器名解析**。
- **当日实测：**

```powershell
docker network create day46-net
docker run -d --name svc-a --network day46-net alpine:3.20 sleep 300
docker run --rm --network day46-net alpine:3.20 ping -c 2 svc-a
# PING svc-a (172.18.0.2) ... 2 received, 0% loss  ← 按名字解析成功
```

- **端口映射：** `-p 6379:6379` = 主机端口:容器端口。不映射时容器端口只在网络内部可达。
- ** Spring 连接模型：** Day23 的 `spring.data.redis.host=127.0.0.1` 能通，正是因为 `redis22` 把 6379 映射到了本机。

### 1.6 Registry（镜像仓库）

- **是什么：** 镜像的「Maven 中央仓库」。`docker pull/push` 的对象。
- **命名规则：** `仓库地址/命名空间/镜像名:标签`，省略仓库地址时默认 `docker.io/library/`。
- **当日实战（故障→解决）：**

| 步骤 | 命令/现象 |
|---|---|
| 直连拉取 | `docker pull redis:7-alpine` → `EOF`（docker.io 被墙/不稳定） |
| 换加速器 | `docker pull docker.m.daocloud.io/library/redis:7-alpine` → 秒下 |
| 打别名 | `docker tag docker.m.daocloud.io/library/redis:7-alpine redis:7-alpine` |
| 验证 | `docker run -d --name redis22 -p 6379:6379 redis:7-alpine` → `PING` 回 `PONG` |

- **根治方法（推荐配置一次）：** Docker Desktop → Settings → Docker Engine，JSON 里加：

```json
{
  "registry-mirrors": ["https://docker.m.daocloud.io"]
}
```

配好后 `docker pull redis:7-alpine` 直连即走加速，不用再写长名字。

## 2. 原理深挖：镜像分层与「写时复制」

```text
镜像（只读）              容器（运行中）
┌─────────────┐        ┌─────────────┐
│ layer3: COPY│        │ 可写层(薄)   │ ← 容器内的一切改动只写这里
│ layer2: apk │   →    ├─────────────┤
│ layer1: OS  │        │ 镜像只读层栈 │
└─────────────┘        └─────────────┘
```

- 删容器 = 删可写层，镜像层不受影响；
- 100 个容器共享同一份镜像层 → 省磁盘、秒级启动；
- 这就是「容器删了数据会丢、Volume 必须外挂」的物理原因。

## 3. 常见错误与排查

| 现象 | 根因 | 处理 |
|---|---|---|
| `pull ... EOF` / 超时 | docker.io 直连不通 | 配 `registry-mirrors` 或用加速器完整路径拉取 |
| `Conflict. The container name ... is already in use` | 同名容器已存在 | `docker rm -f 名字` 或换新名 |
| 容器启动立即退出 | 主进程前台退出（如没带 `-d` 跑常驻命令） | `docker logs 名字` 看输出；`docker run -it` 调试 |
| 应用连不上容器端口 | 没加 `-p` 端口映射 | 补 `-p 主机端口:容器端口` |
| 删容器后数据没了 | 数据写在可写层 | 用 Volume 外挂 |

## 4. 生产环境注意事项

1. **镜像标签别只用 `latest`**：明确版本号，回滚才不抓瞎；
2. **镜像越小越好**：选 alpine/slim 基底，攻击面小、传输快；
3. **永远挂卷存数据**：DB、队列的 data 目录必须 Volume；
4. **自建网络隔离业务**：一组服务一个 network，别都挤默认 bridge；
5. **私有 Registry**：公司内网用 Harbor/Nexus 托管镜像，CI 推送、生产拉取；
6. **容器内别跑多进程**：一容器一职责，进程编排交给 Compose/K8s（Day48/51）。

## 5. 闸门三问

1. 「容器是轻量虚拟机」这句话错在哪？（提示：namespace/cgroups、共享内核）
2. 为什么数据库容器一定要挂 Volume？从镜像分层角度解释。
3. `docker pull redis:7-alpine` 报 EOF，除了配加速器，你今天还用了什么办法拉成功？两种办法的差别是什么？

### 学员作答与批语（2026-09-18）

**第 1 问**

> 学员：它并不像虚拟机一样需要完整操作系统，只是共享宿主机内核。

✅ **通过。** 补全机制：虚拟机 = Hypervisor 虚拟硬件 + 完整 Guest OS（GB 级、分钟级启动）；容器 = 宿主机内核上被 `namespace`（隔离进程/网络/挂载点/主机名）和 `cgroups`（限额 CPU/内存）包裹的普通进程（MB 级、秒级启动）。所以 Windows 上跑 Linux 容器仍需 Docker Desktop 在 WSL2 里藏一个 Linux 虚拟机——**共享的是那个 VM 的内核**。

**第 2 问**

> 学员：Volume 是 Docker 统一管理的寄宿主机存储目录；不挂的话，容器被删除后其他容器无法读取到它写入的内容。

✅ **通过。** 从分层角度再钉一层：容器写入只落在顶部**可写薄层**，删容器 = 删可写层，数据物理消失；镜像层只读共享，改不了。持久化的唯一出路是让数据活在容器文件系统之外 → Volume。这也解释了为何 Volume 挂载点会「遮盖」镜像里同路径的内容。

**第 3 问**

> 学员：配置 registry-mirrors；二者差异请导师补齐。

✅ **通过（差异表如下）。**

| | 加速器完整路径 + tag（当日实操） | `registry-mirrors` 配置（根治） |
|---|---|---|
| 做法 | `docker pull docker.m.daocloud.io/library/redis:7-alpine` → `docker tag` 起短名 | daemon JSON 加镜像地址，重启 Docker |
| 作用范围 | **一次性**，只解决当前这个镜像 | **全局**，此后所有 docker.io 拉取自动走加速 |
| 使用体验 | 每次都要写长路径 + 手动 tag | 直接用 `docker pull redis:7-alpine` 短名，无感 |
| 生效成本 | 无需重启，立刻可用 | 需重启 Docker Desktop |
| 镜像名记录 | 元数据里保留加速器前缀（需 tag 归一化） | 保持 `docker.io` 规范名，无需 tag |
| 局限 | — | 只代理 Docker Hub；gcr.io、quay.io 等仍需各自办法 |

**工程结论：** 临时救火用路径法；本机长期开发必配 `registry-mirrors`；CI/生产环境推私有 Registry（Harbor）才是终极形态。
