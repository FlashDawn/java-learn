## 1. 项目链路（计划原文 ⇄ 代码映射）

```text
POST /tasks?title=xx                ← TaskController.create
      ↓  ① repository.save → PENDING（先落库）
PostgreSQL (tasks 表)
      ↓  ② publisher.publishTaskCreated（后发消息）
RabbitMQ: day35.task.exchange → day35.task.queue
      ↓  ③ @RabbitListener 消费
TaskWorker: 幂等检查 → RUNNING → sleep 1.5s 模拟执行 → DONE
      ↓  ④ 失败时：抛异常 → 本地重试 3 次 → 拒绝
DLQ: day35.task.dlx → day35.task.dlq
      ↓  ⑤ DeadLetterListener
更新状态 FAILED（失败有归宿，不丢消息）
```

顺序铁律：**先落库、后发消息**。反过来 Worker 会回库查不到记录，把正常消息当脏消息丢弃。

## 2. 核心概念（在实战里的落点）

### 2.1 为什么状态必须落库（而不是内存）

- **是什么**：Task 状态机持久化在 PostgreSQL，不再是 Day14 的内存 Map。
- **为什么需要**：MQ 是异步的——消息发出后 Worker 可能几秒后才执行，期间调用方会轮询状态；服务重启内存清空，PENDING 任务就成幽灵。落库后状态可查、可恢复、可审计。
- **代码**：`domain/Task.java`（JPA 实体）、`domain/TaskStatus.java`（四态状态机）
- **坑**：`ddl-auto: update` 仅供学习；生产改 `validate` 并用 Flyway/Liquibase 管理表结构，否则字段变更可能丢数据。

### 2.2 消息只带 ID，不带全量数据

- **是什么**：`TaskMessage` 只有 `taskId + title`，Worker 拿到后回库查最新状态。
- **为什么需要**：消息是「通知」不是「数据拷贝」。若把整个 Task 快照塞进消息，排队期间 DB 被别的请求改掉，Worker 拿到的就是过期数据；且消息体越小，Broker 吞吐越高。
- **代码**：`mq/TaskMessage.java`、`worker/TaskWorker.java` 开头的 `repository.findById`
- **坑**：回库查不到时要正常返回（ACK 丢弃），不能抛异常——否则一条脏消息会占满重试次数再进 DLQ，污染告警。

### 2.3 幂等：重复消息必然出现，业务必须免疫

- **是什么**：MQ 语义是「至少一次投递」，同一条消息可能被投递多次（ACK 丢失、重平衡、重试）。
- **为什么需要**：不防重，「发一次工资」的消息被投递两次就发两次钱。
- **怎么做**：用业务状态做关口——Worker 看到任务已 DONE 直接跳过。这是成本最低的幂等；通用做法是建「已处理消息表」存 messageId 唯一约束。
- **代码**：`TaskWorker` 中 `if (task.getStatus() == TaskStatus.DONE) return;`
- **坑**：幂等判断和状态更新要在同一事务/同一行锁内，否则两个重复消息并发通过检查仍会重复执行（本 Demo 单并发消费未展开）。

### 2.4 Retry 与 DLQ：失败的三段式归宿

- **是什么**：执行失败 → 本地重试（Spring AMQP `retry.max-attempts=3`，间隔 1s）→ 仍失败则拒绝（不 requeue）→ 队列 DLX 参数把死信路由到死信队列 → `DeadLetterListener` 标记 FAILED。
- **为什么需要**：瞬时故障（网络抖动）靠重试自愈；永久故障（数据本身有问题）重试一万次也没用，必须有 DLQ 兜底，否则坏消息卡在队列头反复投递，堵住后面所有消息（队头阻塞）。
- **代码**：`application.yml` retry 段、`MqConfig.taskQueue()` 的 `x-dead-letter-exchange`、`worker/DeadLetterListener.java`
- **坑**：本地重试（JVM 内）适合秒级瞬时故障；需要分钟级间隔的重试要用 RabbitMQ 延迟队列插件或 RocketMQ 的梯度重试（Day31/33 笔记）。

## 3. 生产环境注意事项

### 3.1 消息丢失的三道防线

1. **发送端**：Publisher Confirm 机制——Broker 收到并落盘后回执，没收到回执就重发（本日 ⏭ 未写代码，机制要懂）；
2. **Broker 端**：队列和消息都声明 durable/persistent，Broker 重启不丢；
3. **消费端**：业务处理成功才 ACK（Spring AMQP 容器默认正是如此：Listener 正常返回才确认）。

### 3.2 削峰的量化理解

秒杀 10 万 QPS 直接打 DB 必挂；请求快速落库 + 发消息后立即返回，Worker 按 DB 能承受的 2000/s 匀速消费——峰值被队列「蓄洪」摊平。代价是用户看到的状态是「处理中」，需要前端轮询或 WebSocket 推送结果。

### 3.3 监控清单（生产必做）

队列积压量（queue depth）、消费速率、DLQ 消息数（>0 就该告警）、消费者在线数。

### 参考答案与批语（2026-10-10 学员作答）

**1. MQ 为什么存在？如何削峰、如何异步解耦？**

学员作答：MQ本质是为了满足消费端和生产端之间的异步通讯，在生产环境中使用中间件利用其队列进行缓冲限速，来达到削峰的作用。因为MQ充当中间件，所以相当于业务消费侧和服务提供测不再直接连接，实现了解耦

批语：✅ 三个点全部命中：异步通讯（存在意义）、队列缓冲限速（削峰）、中间件隔开两侧（解耦）。补一层工程视角：解耦的真正红利不只是「不直接连接」，而是**两侧可以独立演化**——Worker 升级、重启、扩容都不影响接收请求的 API；削峰的量化理解见笔记 §3.2（10 万 QPS 被队列蓄洪，Worker 按 2000/s 匀速消化）。

**2. ACK 是什么？Worker 处理完但 ACK 之前宕机会怎样？**

学员作答：ACK是确认信号，使broker知道消息已被消费，可以删除；如果启动了自动确认，则在消息送达后就自动会删。（第二问要求导师代答）

批语：✅ 前半正确。「自动确认送达即删」补充限定：RabbitMQ 原生 `autoAck=true` 才是「送达即删」（处理失败就丢了，危险）；而 **Spring AMQP 默认不是这种**——它在 Listener 正常返回后才发 ACK，抛异常则拒绝/重试，本 Demo 靠的就是这个语义。
第二问标准答案（导师代答）：**处理完、ACK 未发出的瞬间宕机，消息不会丢**——它停留在 Unacked 状态，Broker 发现该 Consumer 连接断开后，把消息 **requeue 重新投递**给下一个 Consumer。代价是这条消息会被**再执行一次**——这正是「至少一次投递」语义和「必须幂等」（第 5 题）的根源。

**3. Retry 解决什么？为什么不能无限重试？**

学员作答：解决了临时故障会使得整条消息消失的问题；重试没有间隔，不限制会反复投递，CPU 被占完，且会让这条故障消息永远挤在队列里，后续消无法进入

批语：✅ 后半满分——「无限重试 = CPU 空转 + 队头阻塞」两个危害都准。前半措辞修一下：重试不是防「消息消失」，而是给**瞬时故障**（网络抖动、下游服务短暂不可用）自愈机会——过几秒再试可能就成功了，不需要人工介入。永久故障（消息本身数据有问题）重试一万次也徒劳，所以必须「有限次 + 间隔递增 + 耗尽进 DLQ」。

**4. DLQ 是什么？什么消息会进去？进去后怎么办？**

学员作答：Dead Letter Queue指的是专门存放无法被正常处理的消息的队列，自然是失败无法被处理的问题消息，集中到这里可以等待人工集中处理

批语：✅ 正确。补全「什么消息会进去」的四种来源：① 被拒绝且不 requeue（含本 Demo 的重试耗尽）；② 消息 TTL 过期；③ 队列满员溢出；④ （RocketMQ）重试次数耗尽自动转入。进去之后的处理不止人工：生产标准是 **DLQ 消费 + 告警 + 修复后 re-drive（重新投递回原队列）**，本 Demo 的 `DeadLetterListener` 标 FAILED 就是自动化处理的最小形态。DLQ 消息数 > 0 应该触发告警（笔记 §3.3）。

**5. 消息幂等是什么？本 Demo 在哪实现？还有哪些方式？**

学员作答：为了防止被重复投递的消息产生多次结果，在 TaskWorker.java:38-42 实现（DONE 状态关口），其他方法要求导师补充

批语：✅ 定义与代码定位都准。其他实现方式（导师补充，按成本从低到高）：
① **业务状态机**（本 Demo）：看 DONE 就跳过，零额外存储，前提是业务本身有状态；
② **唯一约束兜底**：消费结果落库时给 messageId 建唯一索引，重复消费插入直接冲突失败——数据库帮你挡；
③ **去重表/Redis setnx**：消费前 `SET messageId NX EX 86400`，抢不到说明处理过。比状态机通用，适合无状态业务（如纯通知）；
④ **乐观锁/版本号**：更新时带 `WHERE version = 旧值`，重复消息因版本不匹配更新 0 行。
核心思想一句话：**MQ 只保证至少一次，「效果仅一次」永远是业务侧做出来的。**

**6. 消息可能在哪些环节丢失？各环节怎么防？**

学员作答：发送端使用Publisher Confirm 机制防；Broker 端使用 durable/persistent声明防；消费端使用ACK防

批语：✅ 三段防线全对，与笔记 §3.1 逐条对应。补两个深度细节：
- Broker 端的 durable/persistent 只防「Broker 重启」；防「Broker 机器彻底挂掉」还要**镜像队列/仲裁队列（Quorum Queue）**把消息复制到多节点；
- Publisher Confirm 要配合**失败回调重发**才闭环——只开 Confirm 不处理 nack/return，丢失只是「被看见」而不是「被防止」。

**7. 消息重复的根源是什么？为什么 MQ 不直接保证「仅一次」？**

学员作答：因为异步通信延迟和retry

批语：⚠️ 方向沾边但没说透。准确的根源链条：**ACK 丢失或延迟到达**（网络不可依赖）→ Producer/Consumer 无法区分「对方没收到」还是「回执丢了」→ 安全起见只能**再发一次** → 重复不可避免。Retry 只是放大器，不是根源。
为什么不保证「仅一次」：分布式系统里「仅一次投递」等价于要 Broker 和 Consumer 就「这条消息处理完没有」达成**强一致共识**——要么两阶段提交（性能雪崩、分区下不可用），要么像 Kafka Exactly-Once 那样做事务+序列号（实现重、吞吐打折）。工程界的共识是：**传输层做到 at-least-once，把「仅一次效果」交给业务幂等**，成本最低、可用性最高。这就是为什么第 5 题比第 7 题更常考。
