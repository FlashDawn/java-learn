## 1. 概念

### 1.1 Class / Object

- **是什么：** 类是图纸，对象是按图纸 `new` 出来的实例。变量保存的是引用，不是对象拷贝。
- **为什么需要：** 任务平台会有很多用户和任务。不用类就会变成 `userId1, userName1, status1...` 一堆散变量，对不上「这是同一个用户」。
- **怎么做：** 先定义类，再 `new`。`User a = b` 只是两个遥控器指向同一对象。
- **代码：** `day2/User.java`；创建发生在 `Day2App.main` 的 `new User("u-1", "Ada")`
- **坑：** 把引用当拷贝，改 `a` 等于改 `b` 指向的那份数据。生产里传同一个 `Task` 给两个 Worker，会抢状态。

### 1.2 Constructor

- **是什么：** 与类同名、无返回类型的方法，`new` 时自动调用，负责合法初始状态。
- **为什么需要：** 没有构造，对象可以以「没 id、没状态」存在，后面全是 NPE。
- **怎么做：** 构造里给 `final` 字段和初始 `status` 赋值。子类用 `super(...)` 调父类构造。
- **代码：** `User.User(String, String)`；`Task.Task(String, String)`（`protected`，只给子类）；`ImportTask` 里的 `super(id, userId)`
- **坑：** 构造里连库、发 MQ。对象还没出生完就失败，单测极难。构造只摆内存状态。
- **坑：** 忘记 `super(...)`：父类没有无参构造时，子类编译失败。

### 1.3 Encapsulation

- **是什么：** 字段 `private`，只通过方法读/改。非法状态进不了对象。
- **为什么需要：** `status` 若 `public`，任何代码都能写成 `CREATED` 再跳到 `COMPLETED`，和 MQ 重试、重复消费对不齐。
- **怎么做：** `Task` 的 `status` 只能由 `start()` / `complete()` 改；非法转换抛 `IllegalStateException`。
- **代码：** `Task.start`、`Task.complete`、`Task.getStatus`
- **坑：** 给每个字段配一套无校验的 `setXxx`，封装等于没做。
- **坑：** 返回内部可变集合（今天没有）；以后 `getItems()` 若直接返回 `list` 字段，外面仍能改。

### 1.4 Inheritance

- **是什么：** `extends` 表示「是一种」。子类复用父类字段和方法。
- **为什么需要：** 导入任务、同步任务都有 id 和状态机，不该各写一份。
- **怎么做：** `ImportTask extends Task`。能组合就不要为了复用去继承：`Order` 持有 `userId`，**不** `extends User`。
- **代码：** `day2/ImportTask.java` 类声明；对比 `day2/Order.java`
- **坑：** 继承树过深（Task → XxxTask → YyyTask）。Spring Bean、序列化、排错都会痛。优先组合。
- **坑：** 子类破坏父类状态机（所以 `start`/`complete` 在父类标了 `final`，禁止覆盖）。

### 1.5 Polymorphism

- **是什么：** 编译时类型是父类，运行时是子类，调用走子类实现。
- **为什么需要：** Worker 只依赖 `Task`，不必写 `if (导入) ... else if (同步)`。以后加新任务类型少改调用方。
- **怎么做：** `Task task = new ImportTask(...)` 再 `task.type()` / `task.execute()`。`@Override` 写错方法名会编译失败。
- **代码：** `Day2App.main` 中 `Task task = new ImportTask(...)`；`ImportTask.type`、`ImportTask.execute`
- **坑：** 在父类里写 `if (this instanceof ImportTask)` —— 把多态又打回分支。
- **坑：** 该覆盖没加 `@Override`，父类方法改名后子类变成「新方法」，运行仍走父类空实现。

### 1.6 Interface

- **是什么：** 约定能力。一个类可 `implements` 多个接口，只能 `extends` 一个类。
- **为什么需要：** 「能执行」和「能重试」不是继承关系。硬塞进类层次会变成上帝类。
- **怎么做：** `Executable.execute`、`Retryable.maxRetry`。`Task implements Executable`；`ImportTask implements Retryable`。需要重试次数时 `(Retryable) task`（更好的做法是方法参数直接收 `Retryable`）。
- **代码：** `day2/Executable.java`、`day2/Retryable.java`；`Day2App` 的 `(Retryable) task`
- **坑：** 业务到处依赖 `ImportTask` 具体类，换实现要改全项目。Spring 对接口注入就是为了避免这个。
- **坑：** 接口里塞实例字段（Java 里接口字段默认 `public static final`），误当成对象状态。

### 1.7 Abstract Class

- **是什么：** 不能 `new` 的类，可有字段和已实现方法，也可留 `abstract` 方法逼子类实现。
- **为什么需要：** 所有任务共享 id/状态机，但 `type()` / `execute()` 各不相同。纯接口又放不了实例字段 `status`。
- **怎么做：** `public abstract class Task`，`public abstract String type()`。入口只能 `new ImportTask`。
- **代码：** `day2/Task.java`
- **坑：** `new Task(...)` 编译失败（这是故意的）。
- **坑：** 抽象类既当实体又当工具筐，最后谁都不敢改。实例字段只放「所有子类都需要」的东西。

抽象类 vs 接口：实体用抽象类（是一种 Task）；能力用接口（能 execute、能 retry）。

### 1.8 static

- **是什么：** 属于类，不属于某个对象。`static` 方法没有 `this`。
- **为什么需要：** 「当前注册了多少用户」是全局计数，不是某一个 User 的字段。`main` 必须 static，因为启动时还没有实例。
- **怎么做：** `User.registeredCount` + `User.getRegisteredCount()`。实例方法才能碰 `id`。
- **代码：** `User.registeredCount`、`User.getRegisteredCount`；入口 `Day2App.main`
- **坑：** 用 static 存「当前登录用户」。多线程、单测、Web 多请求会串数据。Day 6 再展开。
- **坑：** static 方法里访问 `id`：编译失败，因为没有当前对象。

### 1.9 final

- **是什么：** 赋一次不能再改。字段通常在构造里赋值。`final` 方法不能覆盖；`final` 类不能被继承。
- **为什么需要：** 任务 id、用户 id 中途被改，数据库、MQ、日志就对不上。
- **怎么做：** `private final String id`。状态机方法标 `final`，防止子类绕开校验。
- **代码：** `User.id`、`Order.id`、`Task.id`；`Task.start` / `complete` / `getId` 的 `final`
- **坑：** `final` 的是引用不是对象内容。`final List` 仍可 `list.add`（本 Demo 未用集合）。
- **坑：** 以为 `final` 等于线程安全。不可变要连内部状态都不能改。

### 1.10 Spring 里怎么用（第 1 周只记结论）

- Bean 就是对象，照样要封装；构造注入 = 用构造把依赖传进来。
- 业务依赖 `Executable` / `Task` 这种抽象，容器在运行时塞入 `ImportTask`（多态）。
- 细节第 2 周再写 Spring Boot，今天不要上注解工程。

## 2. 代码导读

| 文件 | 职责 | 关键符号 |
|---|---|---|
| `User.java` | 用户实体 | 构造、`final id`、`static registeredCount` |
| `Order.java` | 订单；组合而非继承用户 | `userId`、`amountFen` |
| `Executable.java` | 能执行 | `execute()` |
| `Retryable.java` | 能重试 | `maxRetry()` |
| `Task.java` | 任务抽象 + 状态机 | `start`、`complete`、`type` |
| `ImportTask.java` | 一种任务 | `extends Task`、`@Override execute/type` |
| `Day2App.java` | 入口 | `Task task = new ImportTask(...)` |

设计原因：计划要求三个领域模型，同时又要覆盖继承/接口/抽象类。所以 `User`/`Order` 保持具体类（组合），`Task` 做成抽象层次展示「是一种 + 能做什么」。

- **线程安全：** Demo 单线程。`User.registeredCount` 若多线程 `++` 会丢计数，生产要用原子类或不要 static。
- **事务：** 无数据库，无事务。
- **异常：** 非法状态转换 → `IllegalStateException`。`java Day2App` 正常路径不抛。若在 `CREATED` 上直接 `complete()` 会失败。
- **测试：** 压缩纯语法包未加 JUnit，用 `Day2App` 打印自检。

短 Review：

- 必须改：无正确性漏洞（正常路径）。
- 建议改：`(Retryable) task` 是教学用强制转换；生产应让方法直接收接口。
- 可延后：JUnit、第二种子类 `SyncTask`、Maven 工程。

## 4. 自测

1. 类、对象、构造、封装各是什么？`Task.start` 为什么不能改成 public 字段赋值？
2. 为什么 `ImportTask extends Task`，而 `Order` 不 `extends User`？接口和抽象类怎么分工？
3. `Day2App` 里 `Task task = new ImportTask(...)` 这一行最关键的是在做什么？若写成 `ImportTask task = new ImportTask(...)` 还算不算多态？

### 参考答案（压缩节奏，导师代写）

1. 类是图纸，对象是实例，构造在 `new` 时初始化，封装用方法守不变量。`status` 若 public，状态机和校验形同虚设，会出现跳步、重复完成。
2. ImportTask **是一种** Task，共享状态机。Order **属于** User，是组合。抽象类放「所有任务都有」的数据和行为；接口放可拼装的能力（执行、重试）。
3. 左边当父类用、右边是子类，之后 `type()`/`execute()` 走 `ImportTask`。变量写成 `ImportTask` 仍会调到子类方法，但调用方绑死具体类，失去「只依赖抽象」的好处，多态的**用法**变弱。

五问结论（学员未作答，导师代写）：

1. 学了 OOP 核心：类对象构造封装，以及继承多态接口抽象类 static final。
2. 需要它们来给 User/Task 划边界，让非法状态进不了对象，并让 Worker 依赖抽象。
3. 解决「散变量管不住状态、每加一种任务就改一串 if」。
4. 不用就只能堆静态方法和 public 字段，后面 Redis/MQ/多线程会失控。
5. 生产坑：引用当拷贝、static 全局状态、继承过深、依赖具体类、`final` 引用内部仍可变。
