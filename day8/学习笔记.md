## 1. 概念

### 1.1 Spring Container

- **是什么：** 管理 Bean 的运行时容器，核心抽象是 `ApplicationContext`。
- **为什么需要：** 手工 `new` 导致依赖网难测、难替换；容器统一创建与装配。
- **怎么做：** `@SpringBootApplication` 启动后得到 Context；`getBean` / 注入拿到实例。
- **代码：** `Day8Application#run` 打印 `container=` / `beanCount=`
- **坑：** 多个 Context（父子、测试）时注入的不一定是你以为的那份 Bean。

### 1.2 Bean

- **是什么：** 由 Container 创建、配置、管理的对象。`User`/`Task` POJO 本身不是 Bean。
- **为什么需要：** 区分「领域数据」与「可复用组件」。
- **怎么做：** 加刻板注解或 `@Bean` 方法注册。
- **代码：** `UserService` 是 Bean；`domain.User` 不是。
- **坑：** 把每次请求的新数据对象误注册成单例 Bean。

### 1.3 IoC 与 DI

- **是什么：** IoC=控制反转（谁创建对象的控制权交给容器）；DI=依赖注入（容器把依赖塞进字段/构造器）。
- **为什么需要：** 解耦；换实现只需换 Bean 定义。
- **怎么做：** 构造器注入（推荐）或 `@Autowired` 字段注入（本包 `TaskService` 演示）。
- **代码：** `UserService(UserRepository)`；`TaskService` 的 `@Autowired UserService`
- **坑：** 字段注入不利于单测与 `final`；循环依赖时构造器注入会启动失败（要正视设计问题）。

### 1.4 Component Scan

- **是什么：** 扫描带 `@Component` 及其派生注解的类并注册为 Bean。
- **为什么需要：** 免写大量 XML/`@Bean`。
- **怎么做：** `@SpringBootApplication` 默认扫描启动类所在包 `com.example.day8` 及子包。
- **代码：** 所有 `@Service`/`@Repository` 均在该包下。
- **坑：** 类放在启动类包外 → 扫不到 → `NoSuchBeanDefinitionException`。

### 1.5 刻板注解

| 注解 | 含义 | 本包类 |
|---|---|---|
| `@Component` | 通用组件 | `BeanLifecycleProbe` |
| `@Service` | 业务层 | `UserService` `TaskService` |
| `@Repository` | 数据访问 | `UserRepository` `TaskRepository` |
| `@Controller` | MVC 控制器 | `AdminHintController` |
| `@RestController` | Controller + ResponseBody | `TaskQueryController` |
| `@Autowired` | 注入点标记 | `TaskService.userService` |

- **坑：** 注解只是语义分层，运行时本质都是 Component；异常翻译等差异主要在 `@Repository`。

### 1.6 Bean 创建 / 注入 / 生命周期要点

```text
扫描/定义 → 实例化 → 注入依赖 → @PostConstruct/初始化回调 → 就绪使用 → 容器关闭 → @PreDestroy
```

- **代码：** `BeanLifecycleProbe` 的 `@PostConstruct` / `@PreDestroy`
- **坑：** 在构造器里用尚未注入的字段；在 `@PostConstruct` 前假设别的 Bean 业务已跑完。
- **坑：** 原型(prototype)作用域与单例混用时生命周期回调行为不同。

#### 重学深挖：Bean 创建流程再拆解

2026-09-11 重学补充，把启动过程再拆细：

```text
1. Component Scan
   扫描 @Component/@Service/@Repository/@Controller 注解的类

2. Bean Definition
   为每个类生成 BeanDefinition（类名、作用域、依赖关系、初始化方法…）

3. 实例化
   按 BeanDefinition 调用构造器 new 对象（默认单例）

4. 依赖注入（DI）
   构造器注入：new UserService(userRepository)
   字段注入：@Autowired 反射塞值（不推荐）

5. 生命周期回调
   @PostConstruct → 就绪使用 → @PreDestroy
```

关键细节：
- 默认 **单例**：整个容器只有一个 `UserService` 实例；
- **构造器注入优先**：能强制依赖齐全、字段可 `final`、便于单测；
- **循环依赖**：A 依赖 B、B 依赖 A，构造器注入会直接启动失败，逼你正视设计问题。

#### 重学深挖：字段注入为什么是「坏味道」

```java
@Service
public class TaskService {
    @Autowired
    private UserService userService;  // 问题在哪？
}
```

1. **隐藏依赖**：看构造器不知道它需要 `UserService`，读代码要翻字段；
2. **无法 `final`**：依赖可以在运行期被反射改掉，对象不可变性被破坏；
3. **半初始化风险**：对象已 `new` 出来但字段还没注入时，若被其他线程/回调拿到就是 NPE；
4. **单测地狱**：想单测 `TaskService`，必须启动 Spring 或用反射塞 Mock，无法 `new TaskService(mockUserService)`。

构造器注入一行解决：

```java
@Service
public class TaskService {
    private final UserService userService;

    public TaskService(UserService userService) {
        this.userService = userService;
    }
}
```

## 4. 自测

1. 用自己的话：什么是 IoC？什么是 Bean？
2. 为什么需要 DI？不用容器会怎样？
3. Demo 里最关键的一行在做什么？（任选注入或生命周期）

### 参考答案

1. IoC：对象创建权交给容器；Bean：容器管理的组件实例。
2. 解耦与可测；到处 `new` 则依赖写死、难替换实现。
3. 例：`UserService` 构造器接收 `UserRepository`——容器在创建 Service 时完成注入；或 `@PostConstruct` 标记初始化完成。

### 2026-09-11 重学批语

| 题 | 原答要点 | 评价与补充 |
|---|---|---|
| 1 | IoC 是大容器，对象/组件在其中创建；DI 是控制权和依赖配置的执行者 | ✅ 方向对；更准：**IoC 是思想，DI 是手段；Bean 是受管对象，不是容器本身** |
| 2 | 字段注入最大问题是隐藏依赖 | ✅ 对了一半；更致命：**无法 `final`**、**半初始化对象逃逸风险**、**单测无法构造 Mock** |
| 3 | 检查 `@SpringBootApplication` 所在包 | ✅ 正确；其次才是注解遗漏、Bean 名冲突 |

五问结论：学了容器装配；为了解耦；不用则手工拼装失控；坑是扫包范围与循环依赖；下一步 AOP。
