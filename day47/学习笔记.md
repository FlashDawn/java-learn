## 0. 当日链路总览

```text
Java 源码
  ↓  mvn -q -DskipTests package          （本机 Maven）
JAR：day14-api-0.0.1-SNAPSHOT.jar (26.1 MB 胖 jar)
  ↓  docker build -t day14-api:1.0 .     （Dockerfile + .dockerignore）
Image：day14-api:1.0（JRE 基底 + jar 层）
  ↓  docker run -d --name day14-app -p 18080:8080 day14-api:1.0
Container：Tomcat 8080（容器内）→ 宿主机 18080 访问
```

**分工认知**：Maven 负责「源码 → jar」；Docker 只负责「jar → 镜像 → 运行」。本日采用**本机打包 + 单阶段 Dockerfile**（KISS）；多阶段构建（Maven 也放进 Docker）见 §4 生产注意。

## 1. 概念与决策

### 1.1 基底镜像：JRE 而非 JDK

- 运行期只需要 JRE；JDK 里的编译器、调试工具在容器里是**死重 + 攻击面**；
- `eclipse-temurin:17-jre-alpine`：Temurin 是 Eclipse 基金会的 OpenJDK 发行版；alpine 变体显著更小；
- 版本对齐：`pom.xml` 里 `java.version=17` → 基底也选 17。

### 1.2 非 root 运行

```dockerfile
RUN addgroup -S app && adduser -S app -G app
USER app
```

- 容器逃逸事故的破坏力与容器内用户权限正相关；生产基线要求非 root；
- 当日验证：`docker exec day14-app whoami` → `app` ✅

### 1.3 `.dockerignore`：精简构建上下文

```text
target/**
!target/*.jar
.idea
*.iml
```

- 构建时整个上下文要传给 Docker daemon；精简后只剩 jar → 传输快；
- 顺带防止源码、`target/classes` 等中间产物进镜像层。

### 1.4 EXPOSE 与端口映射的关系（本日最重要的一个坑）

- `EXPOSE 8080` 只是**文档声明**，不做任何网络绑定；
- 真正生效的是 `docker run -p 18080:8080` = `宿主机端口:容器端口`；
- 两者独立：容器内应用永远听 8080（`application.yml` 不用改），宿主机想映射成什么都行。

### 1.5 JVM 容器感知

- JDK 8u191+ / 11+ 默认开启容器感知：堆上限按 `docker run -m` 限额算，而非宿主机物理内存；
- 本机实测：`docker stats day14-app --no-stream` → `MEM=182.2MiB`；
- 生产常用 `-XX:MaxRAMPercentage=75.0` 给堆外内存留余量。

## 2. 当日两次真实排障（重点复盘）

### 2.1 8080 绑定被拒

| | 内容 |
|---|---|
| 现象 | `docker run -p 8080:8080` → `ports are not available ... bind: An attempt was made to access a socket in a way forbidden by its access permissions` |
| 排查 | `netstat` 未见本机监听 8080 → 不是进程占用；Windows（Hyper-V/WSL2 常驻后）会把某些端口段划入**动态保留范围**，`netsh interface ipv4 show excludedportrange protocol=tcp` 可查 |
| 解法 | 换宿主机端口：`-p 18080:8080`，容器内 8080 不动 |
| 教训 | **宿主机端口是部署细节，容器端口是应用契约**；映射失败只换左边，别改应用 |

### 2.2 PowerShell 中文「乱码」惊魂

| | 内容 |
|---|---|
| 现象 | POST 中文 name 后，PowerShell 里显示 `????`，甚至 `\u` 转义也显示乱码 |
| 排查 | 换 `curl.exe` + `[Console]::OutputEncoding=UTF8` 查询 → 返回 `Docker用户`，**服务端一直是对的** |
| 结论 | 乱码发生在「PowerShell 脚本文件编码 / 控制台显示编码」环节，与应用、容器无关 |
| 教训 | 排查编码问题先换干净客户端（curl.exe）定位责任层；别急着改应用 |

## 3. 常见错误速查

| 现象 | 根因 | 处理 |
|---|---|---|
| 构建时 COPY 找不到 jar | 上下文里没有（先 `mvn package`） | 按链路先出 jar 再 build |
| 构建很慢、上下文几百 MB | 没配 `.dockerignore` | 排除 `target/**` 只留 jar |
| 容器起不来端口冲突/被拒 | 宿主机端口被占或保留 | 换 `-p` 左侧端口 |
| 容器 OOM 被杀 | JVM 按宿主机内存算堆（老 JDK） | JDK 17 自带容器感知；显式 `-m 512m` + `MaxRAMPercentage` |
| 时区差 8 小时 | alpine 默认 UTC | 需要时挂 `/etc/localtime` 或设 `TZ=Asia/Shanghai` |

## 4. 生产环境注意事项

1. **分层 jar**：本日 COPY 整个 26MB 胖 jar，改一行代码整层重来。生产用 Spring Boot layertools 拆 `dependencies / snapshot-dependencies / application` 三层，依赖层万年不变走缓存，变更层只有几百 KB；
2. **多阶段构建**：`FROM maven AS build` 把编译也搬进 Docker，CI 环境零依赖；代价是构建慢、镜像大阶段多，教学日不采用；
3. **健康检查**：`HEALTHCHECK` 或 K8s 探针打 Actuator `/health`；
4. **镜像瘦身三件套**：alpine/slim 基底、`.dockerignore`、多阶段；
5. **别在镜像里塞配置**：`application.yml` 用环境变量覆盖（`-e SPRING_PROFILES_ACTIVE=prod`），镜像才能做到「一次构建，处处运行」。

## 5. 闸门三问

1. 为什么基底选 `17-jre-alpine` 而不是 JDK？为什么必须 `USER app`？
2. 容器内应用监听 8080，你却用 `http://127.0.0.1:18080` 访问——解释两个端口的关系；`EXPOSE 8080` 到底做了什么？
3. 现在每改一行代码，镜像都要重打 26MB 的 jar 层。问题在哪？生产怎么优化？

### 学员作答与批语（2026-09-18）

**第 1 问**

> 学员：运行阶段不需要编译，JDK 全量进容器太笨重；非 root 运行防止容器逃逸事故破坏力过大。

✅ **通过。** 补：alpine 变体进一步瘦身；基底大版本与 `pom.xml` 的 `java.version=17` 对齐。

**第 2 问**

> 学员：运行时做一次端口映射，主要让宿主机端口不被胡乱占用；EXPOSE 仅仅是声明，不做网络绑定。

⚠️ **半对：EXPOSE 全对；映射目的说反了。** 正确方向：容器有独立网络命名空间（Day46 bridge），**不映射时宿主机上什么端口都不占、但服务也完全不可达**；`-p` 是主动在宿主机开门指进容器。标准表述：

```text
容器的 8080 只在 docker bridge 内部可达。
-p 18080:8080 = 宿主机绑定 18080，转发进容器 8080。
不映射 = 零占用，也零可达。
EXPOSE 8080 = 纯文档声明，不做绑定。
```

选 18080 而非 8080，只是绕开 Windows 保留段（§2.1）。

**第 3 问**

> 学员：生产用 layertools 拆 dependencies / snapshot-dependencies / application 三层，依赖层走缓存，变更层只有几百 KB。

✅ **通过（优化方案正确）。** 补全「问题在哪」：镜像层按内容哈希缓存，胖 jar 改一个字节**整层失效**——每次构建/推送/部署都传输 26MB，而实际变更的 class 只有几 KB。拆层后依赖层缓存命中，CI 推送与节点拉取快一个量级。

**闸门结论：三问通过（第 2 问纠正后），Day47 闭环。**
