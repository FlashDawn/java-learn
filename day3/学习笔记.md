## 1. 概念

### 1.1 ArrayList

- **是什么：** 基于动态数组的 `List`，按下标随机访问 O(1)，尾部追加摊销 O(1)。
- **为什么需要：** 用户列表要按顺序存、按索引取；数组定长不够用。
- **怎么做：** `List<User> list = new ArrayList<>(); list.add(...)`
- **代码：** `Day3App.main` 的 `list`
- **坑：** 中部插入/删除要搬迁元素，大数据量中间插删改用 LinkedList 或别的结构。
- **坑：** `list.get(i)` 越界抛 `IndexOutOfBoundsException`。

### 1.2 LinkedList

- **是什么：** 双向链表，既可当 `List` 也可当 `Queue`/`Deque`。
- **为什么需要：** 频繁头尾增删时比 ArrayList 搬迁便宜（本 Demo 用它实现 Queue）。
- **怎么做：** `Queue<String> queue = new LinkedList<>();`
- **代码：** `Day3App` 的 `queue`
- **坑：** 随机访问是 O(n)，不要当 ArrayList 用下标遍历大数据。
- **坑：** 生产队列更常用 `ArrayDeque` 或阻塞队列（Day 7）。

### 1.3 HashMap

- **是什么：** 键值对哈希表，按 key 平均 O(1) 查找。
- **为什么需要：** 「根据用户 ID 找用户」比扫 ArrayList 快一个数量级。
- **怎么做：** `Map<String, User> byId = new HashMap<>(); byId.putIfAbsent(id, user); byId.get(id)`
- **代码：** `Day3App` 的 `byId`、`lookup=`
- **坑：** key 的 `equals`/`hashCode` 必须成对正确；本 Demo `User` 按 id 实现（给 HashSet 用）。
- **坑：** **线程不安全**。多线程并发 put 可能丢数据甚至死循环（旧 JDK）；生产并发读用 `ConcurrentHashMap`。

### 1.4 HashMap 原理（必记）

```text
key → hash(key) → 桶下标 → 链表/红黑树节点 → equals 确认
```

- **hash：** 把 key 打散到数组槽位；分布不均会退化成长链。
- **冲突：** 不同 key 落到同一槽；先拉链，链够长（默认 ≥8 且表够大）转**红黑树**，查改接近 O(log n)。
- **扩容：** 元素数超过 `容量 × 负载因子`（默认 0.75）时，容量翻倍并重新分布。
- **负载因子：** 空间与冲突的折中；太小浪费内存，太大冲突变多。
- **坑：** 扩容瞬间开销大，已知大概规模可预设 `new HashMap<>(expected)`。
- **坑：** 以可变对象当 key 且改了参与 hash 的字段 → 找不到自己。

### 1.5 HashSet

- **是什么：** 基于 HashMap 的不重复集合（元素当 key）。
- **为什么需要：** 用户列表里同 id 出现两次，业务上只要一个人。
- **怎么做：** `Set<User> distinct = new HashSet<>(list);` 依赖 `User.equals/hashCode`
- **代码：** `User.equals` / `hashCode`；`Day3App` 的 `distinct=`
- **坑：** 只重写 equals 不重写 hashCode → Set/Map 行为错乱。

### 1.6 TreeMap

- **是什么：** 按 key **有序** 的 Map（红黑树），操作 O(log n)。
- **为什么需要：** 要按 id 字典序遍历用户，HashMap 无序。
- **怎么做：** `new TreeMap<>(byId)`；key 必须可比较（String 自带）。
- **代码：** `Day3App` 的 `treeFirst=`
- **坑：** key 不能为 null（HashMap 允许一个 null key）。
- **坑：** 不要为了「有序」滥用 TreeMap 做高频随机查找，HashMap 更快。

### 1.7 Queue / Deque

- **是什么：** Queue 先进先出；Deque 双端队列，两端进出。
- **为什么需要：** 任务等待队列、紧急任务插队。
- **怎么做：** `queue.poll()` 取头；`deque.addFirst("urgent")`
- **代码：** `Day3App` 的 `queuePoll=`、`dequeFirst=`
- **坑：** `remove()` 空队列抛异常，`poll()` 返回 null，选错会 NPE 或误杀。

### 1.8 ConcurrentHashMap

- **是什么：** 并发安全的哈希 Map（分段/桶级协作，细节随 JDK 演进）。
- **为什么需要：** HashMap 多线程不安全；全局 `synchronized` 又太粗。
- **怎么做：** `new ConcurrentHashMap<>(byId)`；复合操作用 `compute`/`putIfAbsent` 等原子 API。
- **代码：** `Day3App` 的 `chm`
- **坑：** 迭代时别假设强一致快照；`size()` 在高并发下是估近似值（够用即可）。
- **坑：** 复合「先 get 再 put」仍可能竞态，要用原子方法。

### 1.9 Spring 里怎么用（第 1 周结论）

Service 里常用 `List`/`Map` 缓存请求内数据；跨线程共享用并发集合。不要把请求级 ArrayList 塞进 static。

## 4. 自测

1. 按 ID 查用户为什么优先 HashMap 而不是扫 ArrayList？
2. HashMap 为什么线程不安全？ConcurrentHashMap 解决什么？
3. HashSet 去重依赖对象的什么方法？

### 参考答案

1. HashMap 平均 O(1) 按 key 定位；列表是 O(n)。
2. 并发扩容/写入无同步会丢数据或结构损坏；CHM 提供并发安全的分段/桶级更新与原子 API。
3. `equals` 与 `hashCode` 必须一致；本 Demo 按 `id`。

五问结论（导师代写）：学了常用集合与 HashMap 原理；为了按 ID 查找、去重、排队；不用就只能数组硬扫；生产坑是 HashMap 并发、错误 equals/hashCode、空队列 API 选错。
