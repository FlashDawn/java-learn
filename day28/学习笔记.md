## 1. 概念

### 1.1 Cache-Aside（旁路缓存）读写路径

- **是什么**：应用同时持有缓存和 DB，读时「先缓存、未命中回源 DB、回填缓存」；写时「先写 DB、再删缓存」。这是最常用的缓存模式，也叫 Lazy Loading。
- **为什么需要**：不用缓存，所有读请求都打 DB，磁盘 IO（Demo 里模拟为 100ms）成为瓶颈；用了之后热点数据微秒级返回。
- **怎么做**：读 `getById`：GET 缓存 → null 则 `db.selectById` → SET 回填；写 `updateUser`：`db.update` → `redis.delete`。
- **代码**：`cache/UserCacheService.java` / `getById`、`updateUser`
- **坑**：回填缓存和回源 DB 之间没有加锁时，高并发下同一 key 会被多个线程重复回源——这就是击穿，见 §1.3。

### 1.2 缓存穿透 → 空值缓存

- **是什么**：查询一个**数据库里也不存在**的 key，缓存永远未命中，每次都打穿到 DB。恶意刷不存在的 id 就是穿透攻击。
- **为什么需要**：不防护时，攻击者用不存在 id 高并发请求，DB 直接被打垮。
- **怎么做**：DB 查不到也缓存一个空值占位（本实现用独立 key `nulluser:{id}`），TTL 要短（2 分钟）——太长会把「之后真实创建的用户」挡在缓存外。大规模场景用布隆过滤器（Bloom Filter）在入口拦截。
- **代码**：`UserCacheService` / `isNullCached`、`nullKeyOf`；Demo 场景 2（查 3 次 id=999，DB 只访问 1 次）
- **坑**：空值占位和真实缓存混用同一个序列化器会类型冲突，本实现拆成两个 key 空间（`user:` / `nulluser:`）。

### 1.3 缓存击穿 → 互斥锁重建

- **是什么**：一个**热点 key** 恰好失效的瞬间，大量并发同时未命中，全部回源 DB。与穿透的区别：穿透是 key 不存在，击穿是 key 存在但刚好过期。
- **为什么需要**：秒杀商品这类热点 key 失效瞬间，几百个线程同时查 DB，可能直接把 DB 打挂。
- **怎么做**：未命中时先用 `RedisLock.tryLock` 抢互斥锁，只有抢到的线程回源；其余线程 sleep 50ms 后重读缓存（持锁者已回填）。拿到锁后**双重检查**再读一次缓存，防止等锁期间别人已回填。
- **代码**：`UserCacheService.getById` 锁段；Demo 场景 3（8 线程并发读失效 key，DB 只访问 1 次）
- **坑**：没抢到锁的线程「等待后重读」要有兜底（仍 null 就返回 null 或再试），不能死循环等锁。

### 1.4 缓存雪崩 → TTL 随机抖动

- **是什么**：大量 key 在**同一时刻集体过期**（比如凌晨批量预热了一批 TTL 相同的 key），瞬间流量全打 DB。另一层含义是 Redis 实例整体宕机。
- **为什么需要**：集体失效 = 短时流量放大几十倍，DB 扛不住。
- **怎么做**：TTL = 基础值 + 随机抖动（30min + [0,5min)），让失效时间错开；实例级雪崩靠集群高可用（§1.7）兜底。
- **代码**：`UserCacheService.jitterTtl`
- **坑**：抖动区间别太大，否则短 TTL 的 key 缓存效率下降；一般取基础值的 10%~20%。

### 1.5 Redis 分布式锁

- **是什么**：用所有服务实例共享的 Redis 做仲裁，实现跨 JVM 的互斥。`synchronized` 只能锁单个进程，多实例部署时失效。
- **为什么需要**：多实例下两个节点同时执行「秒杀扣库存」这类临界区，会超卖。
- **怎么做**：加锁 `SET key token NX PX ttl`（一条原子命令：NX 互斥、PX 防持锁者宕机死锁）；解锁用 Lua 脚本「先比对 token 再删」，保证原子性。
- **代码**：`lock/RedisLock.java` / `tryLock`、`unlock`；Demo 场景 4（重复加锁 false → 解锁 → 再加锁成功）
- **坑**：① 拆成 `setIfAbsent` + `expire` 两条命令有死锁窗口；② 直接 `delete` 不解 token 会误删别人的锁；③ 业务执行超过 TTL 锁自动释放，需要看门狗续期（生产用 Redisson）。

### 1.6 数据库与缓存一致性

- **是什么**：写操作后，DB 和缓存如何保持一致。Cache-Aside 的选择是「先写 DB，再删缓存」。
- **为什么需要**：写 DB 后缓存还是旧值，读到的就是脏数据。
- **怎么做**：更新 DB → 删除缓存（不是更新缓存——缓存可能是聚合结果，重建交给下次读的懒加载）。先删缓存再写 DB 的反序做法，中间窗口内并发读会把旧值回填，不一致时间更长。
- **代码**：`UserCacheService.updateUser`
- **坑**：「先 DB 后删缓存」仍有小窗口（删缓存失败 / 主从延迟），强一致场景用「延迟双删」或 Canal 监听 binlog 异步失效。

### 1.7 【补充】Redis 集群

- **是什么**：Redis Cluster 是官方分布式方案：数据按 **16384 个哈希槽（slot）** 分片到多个主节点，每个主节点挂从节点做高可用。key 用 `CRC16(key) mod 16384` 决定落在哪个槽。
- **为什么需要**：单机 Redis 有两个天花板——内存容量（一台机器装不下）和可用性（宕机全停）。集群解决横向扩展 + 故障自动转移。
- **怎么做**：
  - 分片：slot 是迁移的最小单位，扩容时把槽从旧节点搬到新节点（`CLUSTER SETSLOT`）；
  - 高可用：主挂了，从节点自动升主（基于 Raft 式的选举，节点间用 Gossip 协议交换状态）；
  - 客户端路由：key 不在当前节点时返回 `MOVED`（槽已永久迁移）或 `ASK`（迁移中临时转向）重定向，智能客户端（Lettuce）会缓存槽位表。
  - 与哨兵（Sentinel）的区别：哨兵只做故障转移、不分片；Cluster 分片 + 转移一体。
- **代码**：当日无实操（单机容器无法模拟），生产接入点是把 `spring.data.redis.host/port` 换成 `spring.data.redis.cluster.nodes`。
- **坑**：① 多 key 操作（MGET、Lua、事务）要求所有 key 在**同一槽**，否则 CROSSSLOT 报错——用 hash tag `{user:1}.profile` 强制同槽；② 集群模式不支持 `SELECT` 多数据库，只有 db0；③ 主从切换瞬间异步复制可能丢最后几条写入。

### 1.8 【补充】Geode 集群

- **是什么**：Apache Geode（商业版为 VMware GemFire）是内存数据网格（IMDG），Java 生态的分布式缓存/数据平台。与 Redis「单线程 KV 存储」定位不同，Geode 是**点对点（P2P）架构**：没有中心主节点，所有 Server 对等。
- **为什么需要**：超大规模、强一致、需要复杂查询（OQL）或跨机房（WAN）复制的场景，Redis Cluster 不够用时的选择。金融（银行核心、交易所）用得多。
- **怎么做**：
  - **Locator**：集群的发现服务（类似注册中心），新节点先问 Locator 拿到成员列表再加入；本身不存数据；
  - **Server**：存数据的对等节点，数据组织为 **Region**（类似 Redis 的 key 空间 / 表）；
  - Region 两种形态：**REPLICATE**（每节点全量副本，读快、适合小数据量配置）和 **PARTITION**（分片，默认冗余副本数 `redundant-copies`，类似 Redis 的 slot 但按 Region 配置）；
  - 序列化用 **PDX**（跨语言、支持部分字段读取，不用反序列化整个对象）；
  - 跨机房：Gateway Sender/Receiver 做 WAN 异步复制。
- **与 Redis Cluster 对比**：

  | 维度 | Redis Cluster | Geode |
  |---|---|---|
  | 架构 | 主从 + slot 分片 | P2P 对等 + Region 分片 |
  | 一致性 | 最终一致（异步复制） | 可配强一致（同步副本） |
  | 查询 | 按 key 访问 | OQL 类 SQL 查询 |
  | 事件 | keyspace 通知（弱） | CQ 持续查询、监听器（强） |
  | 生态 | 通用、轻量、无处不在 | Java 重型、金融级 |
  | 运维成本 | 低 | 高（Locator/Server/PDX/WAN 都要管） |

- **坑**：① Geode 节点间版本必须严格一致，滚动升级窗口要小心；② PDX 类结构变更要考虑旧数据兼容；③ 脑裂防护靠 membership 仲裁，网络分区时要配 `enable-network-partition-detection`。

### 参考答案与批语（2026-09-24 学员作答）

**1. Redis 为什么快？**

学员作答：redis将要读取的数据预先存在内存中，以此提高读写速度

批语：✅ 抓住主因（内存读写），但「预先存」说法不准——Redis 是**内存优先的存储**，不是把磁盘数据预加载进来。完整答案有四根支柱：
① **纯内存操作**：纳秒级 vs 磁盘毫秒级，这是主因；
② **单线程事件循环**（6.0 前）：无锁竞争、无上下文切换，简单命令反而比多线程更快；
③ **I/O 多路复用**（epoll）：一个线程同时处理上万个连接；
④ **高效数据结构**：SDS 字符串 O(1) 取长度、listpack 紧凑存储、skiplist 支撑 ZSet 范围查询。
面试只答「因为内存」只能拿一半分。

**2. String / Hash / Set / ZSet 分别适合什么？**

学员作答：string适合计数时使用、Hash适合对象有多个字段并经常改某一个，典型案例是用户信息；Set适合不重复的集合；Zset用于需要排序和打分还有延时的

批语：✅ 四个全对，且 Hash 的「改单个字段不用整存整取」和 ZSet 的「延时」（score 存时间戳做延迟队列，正是 Day22 Demo 的 `delay:queue`）都答出了实战味。补全各自一句话锚点：
- String：计数器（INCR）、缓存对象 JSON、分布式锁、Session
- Hash：对象字段级读写（用户信息、商品属性）
- Set：去重集合 + 交并差运算（共同好友、标签）
- ZSet：排行榜、延迟队列、范围分页

**3. 什么是缓存穿透？**

学员作答：查询一个数据库里也不存在的 key，缓存永远未命中，每次都打穿到 DB。恶意刷不存在的 id

批语：✅ 完全正确，与笔记 §1.2 一致。补一句防护选型的权衡：空值缓存适合「不存在的 key 量少且会重复查」；如果攻击者每次换不同的不存在 id（空值缓存失效），就要上**布隆过滤器**在入口拦截。

**4. 什么是缓存击穿？**

学员作答：一个热点 key 恰好失效的瞬间，大量并发同时未命中，全部回源 DB

批语：✅ 完全正确。能区分击穿与穿透（key 存在但刚好过期 vs key 根本不存在）就算真懂了，你的表述里「热点」「恰好失效」两个关键词都在。

**5. 什么是缓存雪崩？**

学员作答：大量 key 在同一时刻集体过期或 Redis 实例整体宕机

批语：✅ 完全正确，两层含义都答到了（key 集体失效 + 实例宕机）。对应防护：前者 TTL 加随机抖动（Demo 的 `jitterTtl`），后者靠集群高可用（§1.7）。

**6. Redis 分布式锁有什么坑？**

学员作答：① 拆成 setIfAbsent + expire 两条命令有死锁窗口；② 直接 delete 不解 token 会误删别人的锁；③ 业务执行超过 TTL 锁自动释放，需要看门狗续期（生产用 Redisson）

批语：✅ 三条全对（笔记 §1.5 原文，说明读进去了）。再补一条更深的坑，集群环境才会踩到：
④ **主从切换丢锁**——客户端 A 在 master 上加锁成功，锁还没异步复制到 slave 时 master 宕机，slave 升主后锁丢失，客户端 B 又能加同一把锁，互斥失效。这就是著名的「RedLock 之争」（Antirez vs Martin Kleppmann）。结论：对正确性要求极高的场景用 ZooKeeper/etcd 锁，或接受 Redis 锁的极小概率失效并加业务兜底（如数据库唯一约束）。

**7. 数据库和缓存不一致怎么办？**

学员作答：更新DB后应删除缓存

批语：✅ 核心动作正确（Cache-Aside 写路径：先写 DB 再删缓存）。补全三个「然后呢」：
① 为什么是**删**不是**改**：缓存可能是聚合结果，改成本高；删掉靠下次读懒加载重建；
② 删失败怎么办：重试 / 延迟双删（删缓存 → 写 DB → 延时几百 ms 再删一次，挡住窗口期回填的脏数据）；
③ 要强一致：Canal 监听 MySQL binlog 异步失效缓存，把缓存维护从业务代码里彻底剥离。

## 5. 故障清单

1. **`ClassCastException: LinkedHashMap cannot be cast to User`**（已修复）：`RedisTemplate<String, Object>` 的 JSON 反序列化拿不到目标类型，默认产出 `LinkedHashMap`。修复：为 User 单独声明类型化 `RedisTemplate<String, User>`（`RedisConfig.userRedisTemplate`）。这是 Day23 已踩过的坑的复现——泛型 Object 模板只能写不能类型安全地读。
2. **8080 端口反复被残留 JVM 占用**（已修复）：`spring-boot:run` 的 fork 进程在 Runner 抛异常后未完全退出，后续启动全部 `webServerStartStop` 失败。修复：按命令行特征清理残留 `java.exe`，并把应用端口改为 18080 避让。教训：Windows 下杀 Maven 不等于杀掉它 fork 的 Java 子进程。
