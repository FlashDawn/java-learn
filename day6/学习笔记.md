## 1. 概念

### 1.1 Thread 与 Runnable

- **是什么：** Thread 是执行流；Runnable 是「要跑的代码」任务。
- **为什么需要：** 10 个任务同时处理，同步 for 太慢。
- **怎么做：** `new Thread(() -> { ... }, "name").start()`；`join` 等待结束。
- **代码：** `Day6App` 两组各 10 线程
- **坑：** 调用 `run()` 而不是 `start()` → 仍在当前线程同步执行。
- **坑：** 无线程上限地 `new Thread`，Day7 要用池。

### 1.2 Callable / Future / FutureTask

- **是什么：** Callable 可返回值并可抛受检异常；Future 拿异步结果；FutureTask 是 Runnable+Future。
- **为什么需要：** 不只「开火忘记」，还要结果（任务处理回执）。
- **怎么做：** `new FutureTask<>(() -> "task-done")` → 线程 start → `futureTask.get()`
- **代码：** `Day6App` 末尾
- **坑：** `get()` 会阻塞；生产常加超时 `get(3, SECONDS)`。
- **坑：** 忽略 Future 里的异常，错误被吃到 `get` 才爆。

### 1.3 synchronized 与竞态

- **是什么：** 互斥锁。同一把锁上的临界区同时只有一个线程。
- **为什么需要：** `unsafeCount++` 不是原子的（读-改-写），10×1000 期望 10000，常更少 → **Race Condition** 破坏 **Atomicity**。
- **怎么做：** `synchronized (LOCK) { safeCount++; }`
- **代码：** `unsafeCount` vs `safeCount`
- **坑：** 锁对象不一致（各锁各的）等于没锁。
- **坑：** synchronized 不保证跨线程「业务多个步骤」的正确顺序以外的可见性细节时，仍要理解 happens-before；简单共享计数用它或 AtomicInteger。

### 1.4 volatile 与可见性

- **是什么：** 保证该变量的写对其他线程**可见**，禁止部分指令重排；**不保证**复合操作原子性。
- **为什么需要：** 工作线程 while 读 `running`，主线程改 false；无 volatile 可能一直看见旧值（Visibility）。
- **怎么做：** `private static volatile boolean running`
- **代码：** `volatile-worker` 循环
- **坑：** `volatile int count; count++` 仍竞态——可见 ≠ 原子。
- **坑：** 用 volatile 代替锁保护整个临界区。

### 1.5 Spring 里怎么用（结论）

Web 请求线程由容器池管理；业务里少自己 `new Thread`。异步用 `@Async` 或显式线程池（Day7）。共享可变状态优先不可变或并发工具。

### 参考答案

1. `++` 非原子，并发丢失更新。
2. 可见性（及有限重排约束）；不能保证 `count++` 原子性。
3. `start` 启动新线程；`run` 只是普通方法调用。

## 4.1 闸门三问：学员回答与批语（2026-09-07）

开课时闸门题顺序为：① `start`/`run` ② 为何 `unsafeCount` 常 &lt; 10000 / `synchronized` 解决什么 ③ `volatile` 能/不能保证什么、与 `synchronized` 分工。

**运行现象（学员确认）：** 多次观察到 `unsafeCount` **不等于 10000**，与竞态预期一致。

### 第 1 问：`start()` 和 `run()` 有什么区别？

**学员回答：**

> start 是使线程开始执行、jvm 调用这个线程的 run 方法，在线程的生命周期中相当于让线程从创建状态转为就绪态。而 run 则是将就绪态且分配到资源的线程进行执行，但其本质只是一个普通调度方法，但必须得等有资源才能执行。

**导师批语：方向对，记法收成一句硬结论。**

- 对的部分：`start()` 之后由 JVM 去调度，最终会在**新线程**里执行 `run()`；`run()` 本身是普通方法。
- 易混点：自己在主线程里写 `thread.run()`，**不会**新建线程，整段 `run` 在**当前线程同步跑完**——这才是最常见坑，比「就绪/运行态」术语更要紧。
- 建议记法：`start()` = 请系统开一条新执行流；`run()` = 任务代码本身，谁调用就在谁的线程里跑。

**评语：通过（需记住「直接调 run = 没开新线程」）。**

### 第 2 问：为什么 `unsafeCount` 经常不到 10000？`synchronized` 解决什么？

**学员回答（原文）：**

> 【volatile】保证写对其他线程可见；不保证 count++ 原子性

**导师批语：答串题了——这句是第 3 问 / volatile 的内容，不是第 2 问。**

第 2 问应对准 `Day6App` 里无锁的 `unsafeCount++`：

- `++` 是读-改-写，不是原子操作 → **Race Condition**，破坏 **Atomicity** → 多次运行常 &lt; 10000（学员已跑通，现象 ✅）。
- `synchronized (同一把 LOCK) { safeCount++; }` 解决的是：**互斥**，让临界区内的 ++ 串行，从而恢复计数原子性；顺带在解锁/加锁之间建立 happens-before，写对其它线程也可见。

请用自己的话补一句：「不到 10000 是因为 ___；synchronized 通过 ___ 修好。」（可写在本段下方，下次回看时填）

**评语：现象通过；书面答案未对准本题，概念需补竞态/原子性，不算完整通过。**

**学员补答（2026-09-07，订正后）：**

> synchronized 修饰代码块称为同步语句块，当运行到这个代码块时会给其上互斥锁使其他想访问当前对象的线程被阻塞，因此其能修好 ++，也具备可见性。

**导师批语：核心结论通过；用词收紧两点。**

1. 锁的是 `synchronized (锁对象)` 里的**那把监视器**（本 Demo 是静态 `LOCK`），不是笼统的「当前对象」。写成 `synchronized (this)` 才是锁 this；锁错对象等于没锁。
2. 被挡住的是「也要拿**同一把锁**才能进临界区」的线程，不是「任何碰到这个对象的线程」。
3. 修好 `++`：靠互斥让读-改-写不被插队（原子性）；退出/进入同步块的 happens-before 带来可见性——这两点你都已点到。

**评语（订正后）：第 2 问通过。**

### 第 3 问：`volatile` 能/不能保证什么？和 `synchronized` 怎么分工？

**学员回答：**

> 仅能保证写入操作对线程的可见性，不保证复合操作的原子性，因此需要能恢复原子性但不具备可见性的 synchronized 进行配合

**导师初评：** 前半正确；「synchronized 不具备可见性」错误。

| | volatile | synchronized |
|---|---|---|
| 可见性 | ✅ 对该变量的写对其它线程可见 | ✅ 退出同步块的写，对之后进入同一锁的线程可见 |
| 复合操作原子性（如 `count++`） | ❌ | ✅（锁住整个临界区时） |
| 典型用途 | 停止旗标、状态发布（单写多读） | 共享可变状态的读改写 |

**学员已用补答明确：`synchronized` 能修好 ++，也具备可见性。**

**评语（订正后）：第 3 问通过。** 分工记成：volatile ≈ 可见；要 `count++` 这类复合操作 → synchronized / 锁 / Atomic*。
